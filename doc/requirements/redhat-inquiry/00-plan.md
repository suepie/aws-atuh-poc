# Red Hat 照会 — 計画と全体像

作成: 2026-08-18 / 目的: **ROSA / RHBK の検証残・公式文書が無いか曖昧な箇所・設計に関わる実現性**を、Red Hat 担当者との面談で確認しきる

---

## 0. なぜ今か

`ADR-056`（ROSA 採用）は **Accepted（条件付き）** で、**採用条件 4 点が未充足**のまま基本設計が進んでいる。加えて `G-DPA`（APPI 28 条）の残ブロッカーが **Red Hat SRE の越境閲覧** 1 点に絞られており、**ここが崩れると基盤構成そのものを再検討**することになる。

**面談は「条件付き」を外す機会**であり、設計全体から未確認事項を漏れなく持ち込む。

## 2. 優先度の考え方

| 優先度 | 意味 |
|---|---|
| **最優先** | **回答次第で基盤構成・契約・金額が変わる**。面談の場で必ず聞く |
| 通常 | 設計の詰めに必要。書面回答で足りる |
| 後回し可 | あると良いが、無くても設計は進む |

## 3. 面談の進め方（推奨）

**G-01（構成レビュー）で全体像を共有してから、D 群（セキュリティ）へ入る。**`G-DPA` は**残ブロッカー 2 件のうちの 1 件**で、ここが崩れると他の質問が無意味になるため早い段階で扱う。

1. **G-01 構成レビュー**（最初に現行構成を説明して意見をもらう。これが後続の議論の土台になる）
2. **D 群 最優先 3 問**（Approved Access / `oc logs` の監査追跡 / SRE 所在地の地理制限）
3. **G-03 / G-04 事例**（法解釈の他社事例・金融機関の事例。D 群の直後が自然）
4. **A 群 最優先 3 問**（3 年契約見積 / cluster fee 割引 / サブスク内包の書面確認）
5. **B・C 群 最優先 4 問**（SPI 互換 / 独自イメージ / 大阪の在庫 / arm64）
6. **G-02 / G-05 / G-06**（バッチ方式 / DR 構成例 / HCP の運用実態）
7. 残りは書面回答を依頼

**面談の場では G 群 6 問 + A〜F の最優先 12 問 = 18 問**に絞る。残 25 問は一覧を渡して書面回答を求める。

### G 群を別立てにした理由

A〜F は「**仕様の事実確認**」で、**書面でも答えが得られる**。一方 G 群は「**他社はどうしているか**」「**この構成をどう思うか**」という**知見・意見を引き出す問い**で、**面談でしか取れない**。

- **書面で足りるもの**（A〜F 25 問）→ 事前に送って回答を待つ
- **会って聞くべきもの**（G 群 6 問 + A〜F 最優先 12 問）→ 面談の議題にする

**時間が足りなくなったら G 群を優先する。**仕様は後から文書で追えるが、**相手の経験は会話でしか引き出せない**。

## 5. Excel への展開方針

**1 シートに 43 問**（実装済み）。`優先度` と `単元` でフィルタして使う。列は次の 9 列 + 回答欄 4 列。

| 列 | 内容 | 用途 |
|---|---|---|
| `RH番号` | `RH-A-01` 形式 | 一意キー |
| `単元` | A〜G | グルーピング |
| `優先度` | 最優先 / 通常 / 後回し可 | 面談で聞く順 |
| **`質問（先方提示用）`** | **平易な日本語。前提知識なしで読める** | **Red Hat に見せる列** |
| **`補足（先方提示用）`** | **背景と、どう答えてほしいか** | **同上** |
| `設計ID` | `ADR-056 残TBD③` `G-SPI-Compat` など | 設計との紐付け |
| `なぜ聞くか` | 社内向けの理由 | 先方には見せない |
| `回答が無いとどうなるか` | ブロックされる作業 | 社内の優先度判断 |
| `出典` | 設計書の該当箇所 | 追跡用 |

**先方に見せるのは `質問` と `補足` の 2 列のみ。**設計 ID や社内事情の列は非表示にして提示する。
