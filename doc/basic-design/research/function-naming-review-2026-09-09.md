## 0. なぜ今ずれているのか

**層が 2 段から 3 段に増えたのに、名前が 2 段のままだから。**

| 層 | 何を表すか | 例 |
|---|---|---|
| 機能グループ | 利用者から見た用途のまとまり | ユーザ管理 |
| **機能名** | **能力の単位**（「〜できる」で言い切れる 1 つのこと） | 顧客からユーザ情報を受け取れる |
| **API**（今回追加） | その能力を実現する呼び出し口 | 登録 / 更新 / 削除通知 / 検索 の 4 本 |

**API の層ができる前は、呼び出し口の違いを機能名で表すしかなかった。** その名残が `SCIM 受信: ユーザの登録 / 更新 / 削除 / 検索` の 4 機能で、**いまはこれは 1 機能 4 API**。同じことが 5 か所で起きている。

## 1. 命名の原則（案）

| # | 原則 | 破っている例 |
|---|---|---|
| **P1** | **機能名は「何を」どうするかが読める。** 主語を省けるのは、機能グループが主語を示しているときだけ | 「JWT の交換」「証明書期限の監視」「項目名の変換・統一」 |
| **P2** | **機能名は能力の単位。呼び出し口の違いは API 層に置く** | 「SCIM 受信: 登録 / 更新 / 削除 / 検索」（4 → 1） |
| **P3** | **設計上の決めごと（何を載せるか・何年残すか・どう分担するか）は機能名にしない。** それを使う機能の作業として WBS の項目名に置く | 「JWT に載せる項目の定義」「監査ログの取得・保管方式」 |
| **P4** | **グループ名に実現手段・製品名を入れない。** 手段は機能名か API で表す | 「ユーザ登録（顧客システム連携・SCIM）」「ローカルログイン（Keycloak-IdP 収容）」「業務システム連携（ServiceNow）」 |
| **P5** | **括弧は「限定」にだけ使う**（対象や方式を絞るとき）。説明を入れない | 「顧客IdPの選択（1 顧客に複数）」は限定なので可。「ユーザ管理（管理画面・API）」は説明なので不可 |

## 2. ご指摘の 4 点への回答

### 2.1 「JWT の交換」— 主語がない

**そのとおり。** 実体は「**ある アプリ向けに出した JWT を、別のアプリ向けの JWT に引き換える**」で、いま想定している唯一の使い道は業務システムから別アプリの API を呼ぶ場面。

| | |
|---|---|
| 現在 | JWT の交換 |
| **案** | **別アプリ向け JWT への交換（Token Exchange）** |
| 理由 | 「何から何へ」が読める。方式名は括弧で限定 |

**あわせて**: いま別グループにいる `業務システムから他アプリへの連携`（F-INT-03）は、**この機能の使い道の 1 つ**であって別の能力ではない。**F-INT-03 を廃止して F-AZ-08 に寄せる**のが素直（工数 1 人日を移す）。

### 2.2 「JWT に載せる項目の定義」— これは機能か

**機能ではない。設計の決めごと。** ただし**捨てる先がある**。

- **能力としての実体は「アプリへ JWT を発行する」**。載せる項目・要求できる範囲・有効期限は、その設計内容
- ぶら下がっている API を見ると裏が取れる。`JWT に載せる項目`（設定）/ `JWT の失効` / `JWT の有効性照会` / `失効の一斉通知` の 4 本で、**どれも「発行した JWT を扱う」API**

| | |
|---|---|
| 現在 | JWT に載せる項目の定義（機能グループ = 認可・権限判定） |
| **案** | **アプリへの JWT 発行**（機能グループ = **JWT の発行**へ移動） |
| 「載せる項目の定義」は | **WBS の作業名として残す**（既に `HJ-07 JWT に載せる項目と要求範囲の定義書` がある）。機能名から降ろすだけで、作業は消えない |
| 影響 | 14 行の付け替え。**認可・権限判定グループから、本基盤が作る唯一の機能が抜ける**ため、同グループは「アプリ責務のみ」になり分担が読みやすくなる |

### 2.3 「証明書期限の監視」— 主語がない

**そのとおり。** 対象は 3 種類ある（`D-12` で整理済み）。

| | |
|---|---|
| 現在 | 証明書期限の監視 |
| **案 A** | **顧客IdP・本基盤の証明書の期限監視**（対象を並べる） |
| **案 B** | **期限が近い証明書の検出と通知**（動作で書き、対象は概要に落とす） |
| **推奨** | **案 A**。「誰の証明書か」が分担の話に直結するため（顧客IdP 側は相手の作業を待つ） |

**同じグループの他 2 つも主語が足りない。**

| 現在 | 案 |
|---|---|
| 署名鍵の定期入れ替え | **JWT 署名鍵の定期入れ替え** |
| 接続用パスワードの定期入れ替え | **アプリの接続用パスワードの定期入れ替え** |

### 2.4 「ユーザ登録（顧客システム連携・SCIM）」— 粒度とグループ

**ご指摘のとおり 3 つ問題がある。**

1. **粒度**: 「ユーザ登録」なら管理画面からの登録も同じグループのはず。実際は別グループ（ユーザ管理）にある
2. **名前**: 「顧客システム連携」は広すぎる。**送ってくるのは顧客IdP**（Entra / Okta 等）が主
3. **層**: 登録 / 更新 / 削除 / 検索の 4 機能は、**能力としては 1 つ**（顧客側の変更を受け取る）で、4 つは呼び出し口の違い

**案**:

| | |
|---|---|
| 機能グループ | `ユーザ登録（顧客システム連携・SCIM）` → **廃止。「ユーザ管理」に統合** |
| 機能名 | `SCIM 受信: ユーザの登録 / 更新 / 削除通知 / 検索`（4 つ）→ **`顧客IdP からのユーザ情報の同期` 1 つ** |
| API 層 | 受信（登録）/ 受信（更新）/ 受信（削除通知）/ 受信（検索）の **4 本**。すでに表にある |
| `SCIM 受信: グループ連携` | Phase 1 対象外のまま、同じ機能の API として残す |
| 工数 | 4 機能分（6.25 人日）を 1 機能に寄せる。**合計は変わらない** |

> **一点だけ確認**: 送信元が顧客の人事システム（IdP ではない）になる可能性が残るなら、機能名は **`顧客システムからのユーザ情報の同期`** の方が安全です。**Phase 1 で顧客IdP 以外から受ける想定があるか**を教えてください。無ければ「顧客IdP から」で確定します。
