# 基本設計 PoC の絞り込みと不足項目の補完

- **日付**: 2026-08-31
- **種別**: research note（クラスタ A の再定義）
- **発端**: ユーザー指示「**基本設計の PoC について、真に必要なものは何か絞ることはできるか。机上や一般的にできるところ、影響が少ないところなどはできるつもりで進めても良い。また、必要なのに不足している項目がないか見てほしい**」
- **結論**: **58 → 41 人日**（-17）。**6 人日を条件付きへ移動**し、**不足していた 3 項目（7 人日）を新規追加**。

---

## 0. 前提の是正（先に発見した不整合）

[00a §A](../00a-remaining-tasks-and-effort.md) の**明細表が 2026-08-27 の移管を反映していなかった**。冒頭に「性能実測 40 人日を ④テストへ移管」と書きながら、**移管済みの 12 行（A-1.1〜1.6 / A-3.4〜3.6 / A-8 / A-10.1 / A-10.2）が表に残り、小計も 98 のまま**だった。本ノートの再定義とあわせて是正する。

---

## 1. 判定基準 — 「実機で確かめる」に値する条件

**3 つすべてを満たすときだけ PoC とする**。1 つでも欠ければ机上・照会・後工程へ回す。

| # | 条件 | 満たさない場合の行き先 |
|---|---|---|
| **①** | **外れたら設計が壊れる**（作り直しが基本設計まで戻る） | 影響が局所なら → **③構築 / ④テスト** |
| **②** | **公開情報・ベンダー照会では分からない**（挙動が文書化されていない、既知の不具合がある、自社の組合せ固有） | 分かるなら → **机上調査 / ベンダー照会** |
| **③** | **後で判明すると高くつく**（契約・調達・他社との取り決めに影響する） | 後で気付いても安いなら → **④テスト** |

> **今回の削減の実体**: 従来の A には「**作る作業**」「**照会で済む確認**」「**後工程と重複する検証**」が混ざっていた。基準を当てると、**残るのは「自社が作る拡張が製品版で動くか」と「相手方の実機との差」の 2 種類**にほぼ収束する。

### 2-4. 条件付きへ移す — A-12 業務システム連携（6 人日）

**理由**: 連携先は 1 つであり、**外れても認証基盤そのものは成立する**（基準①を満たさない）。加えて**連携方式の選択が顧客回答（B-SN-3）待ち**で、回答前に実機検証しても手戻りになる。

→ **分岐 C-A12 を「連携が Phase 1 スコープに入る場合 +6」に置き換え**（従来の C-A12 +3 は本項に統合）。

## 3. 不足していた項目（新規 3 件・7 人日）

**基準①②③をすべて満たすのに A に無かったもの**を洗い出した。

### A-16 🆕 ブランドごとの画面切替が 1 つの基盤で成立するか（3 人日）

| 観点 | 内容 |
|---|---|
| **なぜ必要（①）** | 本設計は「**1 つの認証基盤で複数ブランドの画面を出し分ける**」ことを前提にしている（[ADR-024](../../adr/024-login-ui-customization.md) / [ADR-063](../../adr/063-brand-unit-architecture.md)）。成立しなければ**ブランドごとに基盤を分ける**しかなく、費用構造が変わる |
| **なぜ調べて分からない（②）** | 顧客のまとまりを扱う機能は**製品の新しい機能**で、**その単位で画面テーマを切り替えられるか**の公開情報が乏しい。従来から確実なのは「接続元アプリごとの切替」までで、**組織単位の切替は未確認** |
| **なぜ後では高い（③）** | 画面の見せ方は**顧客への提案内容そのもの**。契約後に「ブランドごとの画面は出せません」は通らない |
| **確認内容** | 組織単位でのテーマ適用 / 接続先の紐付け / 振り分け画面との併用 / 出し分けが効かない場合の代替（接続元アプリ単位への降格）の確認 |

### A-17 🆕 分離した 2 つのネットワーク間の閉域接続が通るか（3 人日）

| 観点 | 内容 |
|---|---|
| **なぜ必要（①）** | [2026-08-27 に 2 ネットワーク分離を本文化](../06-infra-network-design.md)したが、**その到達性は一度も確かめていない**。通らなければネットワーク設計をやり直す |
| **なぜ調べて分からない（②）** | 「**関数の実行環境から閉域接続を経由して認証製品の管理口を叩く**」構成は非自明。**名前解決が経路によって別の宛先に解けるため**（同じ名前が内外で違う先を指す）、実機でないと詰まる |
| **なぜ後では高い（③）** | **ネットワークの区画は作成後に変更できない**。構築に入ってから判明すると全面やり直し |
| **確認内容** | 管理口への到達 / 認証の裏経路への到達 / **逆向きに接続できないこと**の確認 / 名前解決の切り分け / 接続の受け口の作成に要する承認手続と所要時間 |

> **[④テスト IT-08](wbs-test-refinement-2026-08-26.md) と重複しないか**: ④は「作ったものが正しく繋がるか」の確認。**本項は「そもそもこの構成が成立するか」の判断**であり、**ネットワーク設計を確定する前に必要**。目的が違う。

### A-18 🆕 製品ベンダーのサポート範囲の照会（1 人日）

| 観点 | 内容 |
|---|---|
| **なぜ必要（①）** | **自社製の拡張を載せた状態がサポート対象か**が不明のまま。対象外なら**障害時に自力解決**となり、24 時間対応の体制設計（[ADR-040](../../adr/040-pam-jit-admin-privilege-management.md)）の前提が変わる |
| **なぜ調べて分からない（②）** | サポート範囲の詳細は**契約者向けにしか公開されていない**。ただし**照会すれば分かる**ので PoC ではなく**照会作業**（安い） |
| **なぜ後では高い（③）** | **契約前に確定していないと顧客への説明ができない** |
| **照会内容** | 自社拡張を含むイメージの扱い / 独自イメージ配布の可否 / 別系統 CPU への対応可否（A-7 と同時に照会） |

## 6. この絞り込みで受け入れるリスク

| 割り切った内容 | 外れた場合 | 受け皿 |
|---|---|---|
| 切替先の機材確保を**照会だけ**にした | 実際には在庫が無い | 調達計画の見直し（別系統 CPU への切替は既に代替案あり） |
| 記録の可視性を**承認ゲート確認だけ**にした | 実装が個人情報を出していた | [④テスト SEC-06](wbs-test-refinement-2026-08-26.md) で検出（**リリース前には必ず判明する**） |
| 状態変化の即時通知を**机上比較**にした | 自作の方が高くついた | Phase 2 で再評価（Phase 1 は自作前提で設計済み） |
| 業務システム連携を**条件付き**にした | 直前にスコープ入りした | +6 を分岐から充当（**顧客回答 B-SN-3 の取得を急ぐ**ことで回避） |
| 模擬環境（A-5）を**廃止**した | 実機の確保が遅れて旧方式が未検証のまま進む | **実機の手配時期が律速**になる → 実機トライアルの申込を最優先タスクに |

> **最大の残リスク = 実機トライアルの入手時期**。A-6（8 人日）は相手方の試用環境が前提であり、**申込から利用開始までのリードタイムが読めない**。**着手順序としては A-6 の申込を最初に出し、待ち時間で A-2 / A-3 を進める**のが正しい。
