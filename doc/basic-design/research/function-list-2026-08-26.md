# 機能一覧（詳細化）と機能仕様書 WBS の再分割

- **日付**: 2026-08-26
- **種別**: research note（①基本設計 クラスタ **H-B 機能設計**の詳細化。[deliverables](basic-design-deliverables-2026-08-26.md) HB-02〜07 / HB-09〜14 の実体）
- **発端**: ユーザー指示「**基本設計が必要な機能一覧を詳細化して、それごとに WBS をさらに分割したい。現状は認証系・プロビ系と分かれているが、それぞれ何があるのかを細かくしたい**」
- **従前**: HB-02〜07 は「機能一覧 洗い出し（認証系 **15**）」のように**件数の推定値のみ**で、中身が無かった。機能仕様書（HB-09〜14）も系統別 6 行。

---

## 1. 結論 — 機能数は 70（推定）ではなく **91**

| 系統 | 従前の推定 | **実列挙** | 差 |
|---|---:|---:|---:|
| 認証系 | 15 | **22** | +7 |
| プロビジョニング系 | 12 | **17** | +5 |
| 管理コントロールプレーン系 | 18 | **22** | +4 |
| 認可系 | 8 | **9** | +1 |
| 連携系 | 10 | **12** | +2 |
| バッチ系 | 8 | **9** | +1 |
| **合計** | **70** | **91** | **+21** |

**裏取り**: 要件側の**機能要件は 99 件**（FR-AUTH 16 / FR-FED 17 / FR-MFA 11 / FR-SSO 11 / FR-AUTHZ 10 / FR-USER 12 / FR-ADMIN 12 / FR-INT 10）。機能 91 に対し要件 99 で、**1 要件 = 1 機能ではない**（複数要件が 1 機能に集約されるものと、1 要件が複数機能に展開されるものが両方ある）が、**桁として整合**しており列挙漏れは大きくないと判断できる。

## 3. 機能仕様書 WBS = **1 機能 1 行（91 行・57 人日）**

> **2026-08-26 ユーザー指示により中分類 22 行 → 機能ごと 91 行のアトミック版に変更**。
> 「WBS 上でフィルタして機能を絞り、行単位で工数・内容を見たい」ため、**中間集約行を廃止**。
>
> **人日の配分ルール**（合計 57.0 = 91 機能）:
> - **A = 1.0 人日（11 機能）** … 中核かつ複雑（分岐・整合設計が重い）
> - **B = 0.75 人日（24 機能）** … 中核（🔴。基盤の成立に必須）
> - **C = 0.5 人日（56 機能）** … 通常（既存決定の仕様書化が中心）
>
> WBS 上の ID は **`HB-F-<機能ID>`**（例: `HB-F-AUTH-02`）とし、**系統・中核・Phase でフィルタ可能**にする。

## 6. 基本設計（機能仕様書）と詳細設計の境界

2026-08-26 のユーザー指摘「この粒度は詳細設計では？」を受け、**外部設計 / 内部設計の境界**を明示する。従前は両方に「処理フロー」と書かれており**重複していた**（本節で是正）。

| 観点 | ① 基本設計 = **外部設計**（HB-F-*、91 行 57 人日） | ② 詳細設計 = **内部設計**（DD-B、9 行 166 人日） |
|---|---|---|
| **軸** | **機能軸**（91 機能） | **実装単位軸**（103 DU）。機能とは 1:1 でない |
| 概要 | 何をする機能か・誰が使うか | — |
| ルール | **業務ルール・判定条件**（Case 1-6、除外条件など「決めごと」） | それを実現する**アルゴリズム・分岐実装** |
| 入出力 | **外部から見た入出力**（画面項目 / API パラメータ / イベント） | **内部モジュール間の I/F**・データ構造 |
| フロー | **業務の流れ**（利用者・システム間の手順。HB-15〜17 の業務フローと対） | **内部シーケンス図**（コンポーネント間の呼び出し順序） |
| 例外 | **業務例外**（どの条件で拒否し利用者に何を返すか） | **例外処理の実装方式**（リトライ / 補償 / Tx 境界 / DLQ） |
| 構造 | — | **クラス設計・モジュール分割** |
| 関連 | 画面 ID / API / テーブル / 要件 ID（トレーサビリティ） | 実装ファイル・クラスへの対応 |

**判定の目安**: 「**顧客・アプリ利用者に説明する内容**」なら基本設計、「**実装者が手を動かすために要る内容**」なら詳細設計。

**なぜ軸が変わるか**: 基本設計は「何を作るか」を**機能**で数え、詳細設計は「どう作るか」を**実装単位（DU）**で数える。1 機能が複数 DU に跨る（例: F-PROV-12 削除伝播 → DU-U3-05 outbox + DU-U6-05 内部 NLB + shadow 制御 Lambda）ことも、1 DU が複数機能を含む（例: DU-U10-02 idm-api → F-ADM-01〜06 のユーザ CRUD 群）こともある。**この組み替え自体が詳細設計の入口作業**であり、DD-B の初期に「機能 → DU マッピング表」を作る。

**工数への影響**: なし。外部設計に限定しても 0.5〜1.0 人日/機能は妥当（むしろ内部設計まで書くなら 91 機能で 57 人日では到底足りない）。**むしろ従前の記述のままだと「57 人日で詳細設計まで書く」という過小見積りになっていた**ため、本是正は見積りの健全化でもある。
