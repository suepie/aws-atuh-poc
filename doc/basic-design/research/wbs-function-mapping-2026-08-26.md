## 1. 機能列のマッピング規則

> ⚠ **2026-08-26 修正**: 当初は機能 ID（`F-AUTH-02`）だけを入れる想定だったが、**ID のままでは別表を引かないと意味が分からない**ため、**「機能ID」列と「機能名」列の 2 列**に分け、**機能名は平易な日本語**で書くことにした（例: `F-AUTH-02` → **接続先の自動振り分け**）。全 412 行の値は [wbs-text/](wbs-text/) の TSV に生成済み。

**値の書き方**（3 種類のみ。混在させない）:

| 記法 | 意味 | 例 |
|---|---|---|
| `F-AUTH-02` | **特定の 1 機能** | HB-F-AUTH-02、HJ-03（HRD SPI） |
| `F-ADM-01〜06` / `F-BAT-*` | **機能グループ** | HE-04（idm-api ユーザ系 API） |
| **`横断`** | 全機能に効く方式・基盤・管理系 | HA-06（エラー処理方式）、HI-01（レビュー） |
| **`—`** | 機能に紐づかない（インフラ・調達・法務・DR 等） | B-3（CIDR 台帳）、F-3（法務） |

> **原則**: 「その作業の**成果物が、どの機能の実装・提供に直接効くか**」で決める。**迷ったら `横断`** にせず、**主たる 1〜2 機能を書く**（フィルタで拾えることが目的のため）。

## 2. 「内容」列の 2 分割

### 2.1 分割ルール

| 新列 | 書き方 |
|---|---|
| **A. 概要** | **平易な日本語で「何をするのか・なぜ要るのか」を 1〜2 文**。**外部 ID（ADR-0xx / D-Ux-nn / §x.y / DU-xx / G-xxx）は書かない**。使ってよい ID は **この WBS 内のもの（A-1.1 / HB-F-AUTH-02 / F-PROV-12 など）だけ**。専門用語は残してよいが、略号は初出で開く（例: 「HRD（ログイン画面でどの接続先に飛ばすかを判定する仕組み）」） |
| **B. 成果物と完了条件** | **何が出来上がるか（成果物）＋ 何をもって終わりとするか（完了条件）**。**測定可能・判定可能**に書く。外部 ID はここに置いてよい（出典列があるならそちらへ寄せる） |

> **要点**: 概要は「**この行を初めて見た人が理解できる**」ことが目的。成果物・完了条件は「**終わったかどうかを他人が判定できる**」ことが目的。

### 2.2 書き換え例（クラスタ別）

| 現行の「内容」 | **A. 概要** | **B. 成果物と完了条件** |
|---|---|---|
| A-1.2「フェデ/HRD 解決の p99（ベースライン比 +10% 以内で判定）」 | 接続先が 1000 社を超えても、ログインの待ち時間が実用の範囲に収まるかを実測する | 測定レポート。1000/2000 接続時の応答時間が基準比 +10% 以内であることを数値で示す。超過時は A-1.7 で対策を設計 |
| A-2.2「HRD / JIT 案 B / Re-Activation / mfa_indicator の各機能互換」 | 商用版の Keycloak でも、自社で作った 4 つの拡張機能が同じように動くかを確かめる | 検証結果表。4 機能すべてが商用版で動作し、動かない場合の代替方針が決まっている |
| C-1.1「『27 Pod』不整合是正・少数大型 Pod モデルへの設計判断」 | 設計書の中でサーバー台数の記述が食い違っているので、正しい考え方に統一する | 是正後の設計記述。台数の根拠が 1 つに揃い、他の章と矛盾しないことをレビューで確認 |
| D-17.2「D3-04 経路表・provisioned_by=local-admin 限定」 | 利用者が「どの経路で登録されたか」の区分を、全員フェデレーション化した方針に合わせて整理し直す | 改訂後の経路表。管理者が作った利用者だけが特定の区分になり、他経路と重複しないことを確認 |
| HB-F-PROV-12「削除伝播（outbox→shadow 制御）」 | 利用者を削除したとき、その事実がもう一方のシステムにも必ず伝わるようにする（`F-PROV-12`） | 機能仕様書 1 本。削除の判定条件・利用者への応答・関連画面/API/テーブルが書かれ、レビュー承認済み |
| HC-05「画面仕様書 管理 SPA 系（20 画面 × 0.5）」 | 管理者が使う 20 画面について、画面の項目・入力チェック・権限による表示の違いを決める | 画面仕様書 20 本。各画面の項目定義・チェック内容・権限別表示が揃い、画面一覧と 1 対 1 で対応している |
| HE-13「Webhook 仕様（7 種・署名・再送）」 | 利用者の変更をアプリ側へ通知する仕組みについて、通知の種類と受け取り方の決まりを定める | Webhook 仕様書。7 種類の通知内容・署名方式・再送回数が定義され、受信側の実装要件が書かれている |
| HJ-03「HRD Authenticator クラス設計」→ **基本設計側は HJ-03 ではなく仕様** | ログイン画面で入力された ID からどの接続先へ飛ばすかを判定する拡張機能の、入出力と動作条件を決める | SPI 仕様書。入力・出力・判定できない場合の振る舞い・組み込み位置が定義され、実装者が着手できる |
| GD-16「アクセストークン検証（RS 必須 7 点、`aud`=account 罠）」 | アプリ側が受け取った通行証を正しく検証するための必須チェック項目を、ガイドの 1 章として書く | ガイド 1 章。7 つの検証項目と、設定を誤ると検証が素通りする落とし穴の警告が書かれ、レビュー済み |
