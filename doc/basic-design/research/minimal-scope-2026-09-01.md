# 最小構成の見積り — フェデレーション + 利用者収容に絞った場合

> 🔵 **2026-09-02: 本ノートの判定（必須 321 / アプリ分担 39 / 別途切り出し 55 / 必須（縮小）35）は WBS の列から外した**（ユーザー判断）。**採用した決定ではなく「さらに絞るなら」の仮定**であり、決定済みの軸（構成前提・アプリ移管）と混ざって読み違えるため。**再検討する場合は本ノートを起点に再計算する**。

- **日付**: 2026-09-01
- **種別**: research note（スコープ分割の検討）
- **発端**: ユーザー指示「**最低限のフェデレーション、IdP としての機能だけあればよく、他はアプリ分担か別途切り出したい**」
- **結論**: **91 機能 → 48 機能**（53%）。**① 基本設計 750 → 561 人日（-189 / -25%）**。
- ⚠ **重要**: **機能を 47% 落としても工数は 25% しか減らない**。理由は §5 に示す。

---

## 1. 「最小構成」の定義

**残すもの＝「顧客の認証システムに委譲でき、持たない顧客には自分で認証を提供でき、退職者を確実に止められる」まで。**

| 残す | 出す |
|---|---|
| 顧客の認証システムへの委譲（新旧 2 方式） | **誰が何を使ってよいかの管理（権限）** |
| 自社での ID・パスワード認証（顧客側に仕組みが無い場合） | **アプリの入口画面・アプリ一覧** |
| 委譲した相手からの利用者の自動登録と属性の反映 | **顧客システムからの一括受信** |
| **退職者の遮断とその確実な伝播** | **業務システムとの連携** |
| 管理者による利用者・接続先の登録と管理 | **不正検知・外形監視** |
| 監査記録 | **棚卸し・同意管理・一括入出力** |

## 2. 3 つの行き先の定義

| 記号 | 行き先 | 意味 |
|---|---|---|
| **必須** | 本基盤（最小構成） | **これが無いと「認証基盤」として成立しない** |
| **アプリ分担** | 各アプリ側で実装 | **アプリが自分で持てる**。基盤は識別子だけ渡す |
| **別途切り出し** | 後続フェーズ / 別プロジェクト | **後から足せる**。無くても認証は成立する |

## 5. ⚠ 最小構成を選ぶ前に知っておくべき 4 点

### 5-1. 🔴 機能を 47% 落としても工数は 25% しか減らない

**減らない領域が全体の半分近くを占める**ため。

| 減らない領域 | 人日 | 理由 |
|---|---:|---|
| 他組織との連携（B） | 23 | ネットワーク・入口・外向き通信の要求は**機能数と無関係** |
| 全体・方式設計（H-A） | 48 | 異常時の扱い・記録・番号体系は**1 機能でも 91 機能でも同じ** |
| 運用補完（H-H）・災害対策 | 12+ | **仕組みの数ではなく構成の複雑さで決まる** |
| 契約・法務（F, H-K） | 32 | **顧客に約束する内容は機能数で変わらない** |

### 5-2. 🔴 「アプリ分担」はコストが消えるのではなく移る（しかも増えうる）

権限管理をアプリ分担にすると、**アプリごとに同じものを作る**ことになります。

| | 基盤で持つ場合 | アプリ分担にした場合 |
|---|---|---|
| 権限テーブルの設計・実装 | **1 回** | **アプリの数だけ** |
| テナント越境の防止 | 基盤が一元的に強制 | **各アプリが自力で実装**（漏れれば事故） |
| 権限の棚卸し | 1 か所で完結 | **アプリごとにバラバラ**（監査時に集約困難） |

→ **アプリが 3 つ以上あるなら、基盤で持った方が総額は安くなる可能性が高い**。**アプリ数の見込みが判断材料**です。

### 5-3. 🟡 接続先の振り分けを外すと、顧客ごとに URL が分かれる

代替手段は「**顧客ごとに入口 URL を分ける**」です。技術的には成立しますが:

- 利用者は**自分の顧客専用 URL を覚える**必要がある（ブックマーク運用）
- **共通の入口から入れない**ため、複数顧客にまたがる利用者は URL を使い分ける
- 後から共通入口へ移行するとき、**利用者への周知が必要**

一方で、**振り分けは自社製の拡張が必要な最大の技術リスク**（[PoC A-2.2](poc-scope-narrowing-2026-08-31.md)）でもあります。**外せばリスクも消えます**。

### 5-4. 🔴 アプリ向け実装ガイド（108 → 94）はあまり減らない

**むしろアプリ分担が増えるほど、ガイドに書くことは増えます**（権限判定・テナント越境防止をアプリ側で正しく作らせる必要があるため）。**機能を基盤から出すほど、伝えるべきことは増える**という関係にあります。

## 7. 【2026-09-02 追記】利用者管理もアプリへ任せる場合

ユーザー問い「**利用者を追加・削除・編集する機能もアプリに任せるとすればどうか**」への試算 → [minimal-scope-idp-delegation-2026-09-02.md](minimal-scope-idp-delegation-2026-09-02.md)

**解釈が 2 通りあり、規模がまったく違う**:

| | **案 A: 画面だけ任せる** | **案 B: 利用者そのものを持たない** |
|---|---:|---:|
| ベース総計 | **1,673**（-70 / -4%） | **1,272**（-471 / -27%） |
| クラスタ数 | 2 | **1** |
| 認証システムを持たない顧客 | 受け入れ可 | **受け入れ不可** 🔴 |

- **案 A の効果は限定的**。**API は残さざるを得ず**（認証製品を触れるのは本基盤だけ）、**画面が無くなる分 API 側の権限確認が厚くなり**、ガイドも増えるため。**効果は構築（-45）に出て、基本設計はほぼ変わらない（-3）**。
- **案 B は効果が大きいが事業判断**。「認証システムを持たない顧客を取らない」が前提で、**委譲比率の暫定値 50:50 が実勢なら半数の顧客を切る**ことになる。
