# ネットワーク分離は本当に効くのか — 侵害リスクの深掘り

- **日付**: 2026-09-02
- **種別**: research note（構成の見直し 3 件目）
- **発端**: ユーザー問い「**分離したところで管理 API 側から認証製品にアクセスするのであれば、外からは見えはするので防御は変わらないのか。それとも分離することに大事な意味があるのか**」
- **結論**: **ご指摘は半分正しい**。到達はする。**しかし「何が取れるか」が決定的に違う**。ただし**分離だけでは不十分**であり、セットで必要な防御がある。

---

## 1. ご指摘の正しい部分 — **到達はする**

分離しても、**管理 API は認証製品の管理用の口に到達する**。これは設計上そうしている（利用者を作る・消すため）。

したがって **「管理 API が侵害されたら、管理用の口でできることは全部できる」** のは**分離してもしなくても同じ**。

| 侵害後にできること | 1 ネットワーク | 2 ネットワーク |
|---|---|---|
| 利用者の作成・削除 | ✅ できる | ✅ **できる** |
| 利用者の属性の書き換え | ✅ できる | ✅ **できる** |
| **パスワードの設定（なりすまし）** | ✅ できる | ✅ **できる** |
| 接続先の追加（偽の認証システムを登録） | ✅ できる | ✅ **できる** |

> **ここは差が無い**。**「分離すれば安全」ではない**。

---

## 2. 🔴 決定的に違う部分 — **パスワードのハッシュが取れるかどうか**

| | 1 ネットワーク | **2 ネットワーク** |
|---|---|---|
| DB への経路 | 🔴 **存在する**（接続許可の設定で塞ぐ） | ✅ **存在しない** |
| **パスワードのハッシュの一括取得** | 🔴 **設定が破れれば全件取れる** | ✅ **取れない** |

**なぜ「取れる／取れない」が決定的か**:

**認証製品の管理用の口は、パスワードのハッシュを返さない**（書き込めるが、読み出しでは伏せられる）。一方 **DB を直接読めばハッシュが全件取れる**。

| | 取れるもの | 攻撃者にとっての価値 |
|---|---|---|
| 管理用の口 | 利用者の情報（ハッシュ以外） | その基盤の中でしか使えない |
| **DB 直接** | 🔴 **パスワードのハッシュ全件** | 🔴 **時間をかけて元のパスワードを割り出せる。他サービスでの使い回しに波及する** |

> **ハッシュを持ち出されると、被害が本基盤の外へ広がる**。利用者は同じパスワードを他所でも使っているため。**これが「取れる／取れない」を分ける最大の理由**。

### 事後対応も変わる

| | 1 ネットワーク（ハッシュ流出） | 2 ネットワーク（管理口の悪用のみ） |
|---|---|---|
| 対応 | 🔴 **全利用者のパスワード強制リセット** | 影響を受けた利用者の特定と復旧 |
| 報告 | 🔴 **重大な漏えいとして報告義務** | 不正アクセスとして報告 |
| 顧客への影響 | 🔴 **全顧客・全利用者** | **限定的** |

---

## 3. その他の 3 つの差

### 3-1. 探索できる範囲

| | 1 ネットワーク | **2 ネットワーク** |
|---|---|---|
| 侵害後に見える範囲 | 🔴 **クラスタ網全体**（ノード・内部の口・各種エンドポイント）を順に調べられる | ✅ **管理用の口 1 つだけ**。他は**経路が無いので存在すら分からない** |

> **攻撃は「何があるか調べる」ところから始まる**。**調べられないことに意味がある**。

### 3-2. 🔴 記録に残るかどうか

| | 1 ネットワーク | **2 ネットワーク** |
|---|---|---|
| DB を直接読む | 🔴 **認証製品の記録には残らない** | — |
| 管理用の口を叩く | ✅ 全操作が記録される | ✅ **全操作が記録される** |

> **分離すると、攻撃者は「記録が残る経路」しか使えなくなる**。**検知と追跡ができる**。

### 3-3. 逆向きに来られるか

**閉域接続は呼ぶ側 → 呼ばれる側の一方向**。

| | 1 ネットワーク | **2 ネットワーク** |
|---|---|---|
| 認証製品側が侵害されたら | 🔴 **管理面へも到達できる** | ✅ **逆向きに接続を張れない** |

---

## 4. 🔴 分離が防がないこと（正直に）

| 防げないこと | 内容 |
|---|---|
| **管理用の口の悪用** | 資格情報が漏れれば、**利用者の作成・削除・パスワードの設定は全部できる** |
| **なりすまし** | 🔴 **ハッシュを読めなくても、パスワードを書き換えれば任意の利用者になれる** |
| **偽の接続先の登録** | 攻撃者が用意した認証システムを登録し、そこから入る |

> **分離は「持ち出し」を防ぐが、「悪用」は防がない**。

### だからセットで必要な防御

| # | 防御 | 何を防ぐか | 現行の設計 |
|---|---|---|---|
| 1 | **管理 API の資格情報を短命にする・定期的に入れ替える** | 漏れても使える時間を限る | ✅ 90 日入替（[U7](../07-security-compliance-design.md)） |
| 2 | **全操作を記録する** | 悪用の検知と追跡 | ✅ 操作記録（F-ADM-18） |
| 3 | **管理操作の 3 段階権限確認** | 1 つの資格で全部できない状態にする | ✅ F-AZ-06 |
| 4 | **テナント越境の防止** | 1 顧客の侵害が全顧客に及ばない | ✅ F-AZ-05 |
| 5 | 🔴 **異常な操作の検知**（大量削除・大量パスワード変更） | **悪用の早期発見** | 🔺 **不正の検知（F-INT-08）は「別途切り出し」判定** |

> 🔴 **#5 が「別途切り出し」のままだと、分離で防いだ後の「悪用」に気づけない**。**分離とセットで見直すべき**。

---

## 5. 結論

| 問い | 答え |
|---|---|
| **分離しても到達はするのでは？** | ✅ **そのとおり**。管理用の口には到達する |
| **では防御は変わらないのか？** | ❌ **変わる**。🔴 **パスワードのハッシュを一括で持ち出せるかどうかが決定的に違う**。**被害が本基盤の外へ広がるかどうかの分かれ目** |
| **分離すれば安全か？** | ❌ **違う**。**悪用は防げない**。資格情報の管理・記録・権限の分割・異常検知とセットで初めて成立する |

### 判断

| | 削減 | 失うもの |
|---|---:|---|
| **分離をやめる** | **-36**（全体の 1.7%） | 🔴 **ハッシュの一括持ち出しを構造的に防ぐ唯一の手段** |

**維持を推す**。ただし **§4 の #5（異常な操作の検知）を「別途切り出し」から戻すこと**を条件とする。**分離だけでは片手落ち**のため。

---

## 6. 🔴 前提の裏取りが必要

本ノートの中核は「**認証製品の管理用の口はパスワードのハッシュを返さない**」という前提に立っている。**この前提が崩れると結論が変わる**ため、実機で確認する。

| 確認項目 | 人日 |
|---|---:|
| **A-20** 🆕 **管理用の口から利用者の資格情報を読み出したとき、ハッシュが伏せられることの実機確認** | **+0.5** |

> **0.5 人日で、分離を維持する根拠の妥当性が確定する**。**この確認をせずに「分離すれば安全」と説明してはならない**。
