# 「認証製品のガワだけ」案の検討

- **日付**: 2026-09-02
- **発端**: ユーザー依頼「**認証製品のガワだけで、中身を作るのはアプリ（振り分けや利用者の控えの管理を含む）であればどうなるか**」
- **結論**: **工数は約半分になるが、🔴 認証基盤としての前提が 2 つ壊れる**。**アプリ数が 5 つを超えると総額でも不利**。

---

## 1. 何を「ガワ」と呼ぶか

| | 本基盤（ガワ） | アプリ（中身） |
|---|---|---|
| 認証製品が動く基盤（設備・DB・ネットワーク） | ✅ | |
| 空間（Realm）の器・製品標準機能の初期設定 | ✅ | |
| 監査記録・鍵の入替・法令対応・契約 | ✅ | |
| 運用（監視・手順書・バックアップ） | ✅ | |
| **接続先の振り分け** | | 🔴 **アプリ** |
| **利用者の控えの管理** | | 🔴 **アプリ** |
| 利用者の登録・変更・削除 | | アプリ |
| 権限・画面・つなぎ目の設計 | | アプリ |

## 3. 🔴 技術的に成立するか — **2 つは成立し、1 つは成立しない**

### 3-1. ✅ 接続先の振り分け — **成立する**

アプリ側で振り分け画面を作り、**判定結果を製品に渡す**方式が製品標準機能として用意されている。**自社製の拡張は不要になる**（現在の最大の技術リスクが消える）。

**ただし代償がある**:

| 代償 | 内容 |
|---|---|
| **アプリの数だけ振り分け画面を作る** | 顧客が同じ画面を何度も見ることになる |
| 🔴 **判定に必要な情報をアプリへ配る必要** | 「どの顧客がどの接続先か」の一覧を全アプリへ配布し、**変更のたびに同期**する |
| **入口が分散する** | 共通の入口から入れなくなる |

### 3-2. ⚠ 利用者の控えの管理 — **成立するが条件つき**

アプリが管理用の口を直接叩けば可能。**ただし下記 3-3 の問題を伴う**。

### 3-3. 🔴 管理用の口の資格をアプリへ渡す — **ここが成立しない**

**「ガワだけ」にすると、本基盤は管理用の API を作らない**。するとアプリは**認証製品の管理用の口を直接叩く**ことになる。

| 問題 | 内容 |
|---|---|
| 🔴 **テナント越境を止められない** | **1 つのアプリの資格情報が漏れると、全顧客の利用者を操作できる**。製品の管理用の口には「この顧客の分だけ」という制限をかける仕組みが無い |
| 🔴 **なりすまし** | パスワードを書き換えられるため、**任意の利用者になれる** |
| 🔴 **記録が「アプリがやった」までしか残らない** | どのアプリの誰が操作したかの追跡が困難 |

> **これは先に「認証製品の管理用の口をアプリに直接叩かせることはできない」と結論した論点そのもの**。**ガワだけ案はこの結論と正面から衝突する**。

**回避するには結局「管理用の API を本基盤が作る」ことになり、ガワだけではなくなる**（現在の案 C に戻る）。

---

## 4. 🔴 判断材料 — **アプリ数が損益分岐点**

**基盤が減った分は、アプリ側に移るだけ**である。

| アプリ数 | 基盤の削減 | **アプリ側の増加**（1 アプリ 120 人日想定） | 総額 |
|---:|---:|---:|---|
| 1 | -1,050 | +120 | 🟢 **大幅に有利** |
| 3 | -1,050 | +360 | 🟢 有利 |
| **5** | -1,050 | **+600** | 🟡 **拮抗** |
| 10 | -1,050 | **+1,200** | 🔴 **不利** |

> **アプリ 1 つあたり 120 人日**の内訳: 振り分け画面 20 ／ 利用者管理の画面と処理 40 ／ 権限 30 ／ 控えの管理 20 ／ 試験 10。

**加えて、金額に表れない損失がある**:

| 損失 | 内容 |
|---|---|
| 🔴 **品質のばらつき** | **アプリごとに認証まわりを実装するため、1 つでも作り方を誤ると事故になる** |
| 🔴 **共通化の価値が消える** | **「共通の認証基盤を作る」という目的自体が薄れる** |
| **実装ガイドが激増** | 108 → **160 前後**。**全部アプリに作らせるため、書くことが増える** |
| **責任分界が複雑化** | 事故が起きたとき、基盤とアプリのどちらの責任かが曖昧になる |

---

## 5. 結論

| 問い | 答え |
|---|---|
| 工数は減るか | ✅ **約半分（2,180 → 1,130）** |
| 技術的に成立するか | 🔺 **振り分けは成立する。🔴 管理用の口の資格をアプリへ渡す点が成立しない** |
| 総額で得か | 🔺 **アプリ 5 つ未満なら得。それ以上は損** |
| 推奨するか | ❌ **しない**（下記） |

### 推奨しない理由

1. 🔴 **管理用の口の問題が回避できない**。回避するには API を作ることになり、**結局ガワだけではなくなる**
2. 🔴 **テナント越境の防止を各アプリに委ねることになり、1 つの実装ミスが全顧客に及ぶ**
3. **共通基盤を作る目的と矛盾する**

### ただし部分的には採れる

| 採れる部分 | 効果 |
|---|---:|
| ✅ **接続先の振り分けをアプリ側へ**（判定結果を渡す方式） | **-17 ＋ 最大の技術リスクが消える** |
| ✅ 画面をアプリ側へ（既に案 C で実施済み） | 実施済み |
| ❌ 管理用の口の資格をアプリへ渡す | **採らない** |

> **「ガワだけ」の考え方のうち、振り分けの部分は採用価値がある**。**A-2.2（自社拡張の互換検証）という最大の技術リスクが消える**ためである。
