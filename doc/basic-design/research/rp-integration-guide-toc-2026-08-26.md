## 1. 調査で判明した重要事実 3 件（設計への影響あり）

### ⚠ 1-1. `draft-ietf-oauth-browser-based-apps` は **RFC 化済み（RFC 10017 / BCP 212、2026-08 発行）**

社内資料（[U5 §5.6.2](../05-token-session-authz-design.md) ほか）は「IETF Internet-Draft」と記載しており、**全箇所の改訂が必要**。かつ **implicit の禁止強度が SHOULD NOT → MUST NOT に上がっている**（RFC 9700 §2.1.2 は SHOULD NOT、RFC 10017 §7.2 は MUST NOT）。→ **アプリ向けには強い方（MUST NOT）で統一**する。
出典: https://www.rfc-editor.org/rfc/rfc10017.html

### 🔴 1-2. Keycloak は既定で **アクセストークンの `aud` が `account`** → 「aud 検証している"つもり"」が量産される

Keycloak の AT は既定 `"aud": "account"`（ID Token は `client_id`）。**RS 側で `aud` を厳格検証するには Audience Mapper / Client Scope の明示設定が必須**。設定漏れのまま「検証済み」と主張するアプリが出るのが典型。さらに **Keycloak 26.6.2 で introspection の `aud` 強制が入り（CVE-2026-37979）、未設定サービスが突然 401 になった**事例あり。
→ **本基盤固有の "全 RP が同じ穴を掘る罠"**。ガイドの P0 項目とし、**Client 登録テンプレート（HJ-09）側で Audience Mapper を既定同梱**する。
出典: https://github.com/keycloak/keycloak/issues/12415

### 🔴 1-3. Keycloak 公式が「レルム公開鍵のハードコード」を**許容表現で記載**

Keycloak "Recommendations" は「公開鍵をハードコードするか certificate endpoint から取得する」と両論併記。鍵ローテーションで確実に壊れる。Microsoft は同じ論点を「**単一署名鍵しかサポートしないアプリは本質的に安全性・信頼性が低い**」と断定。
→ **自社ガイドで明示的に禁止**し、Microsoft のキャッシュ基準を採用（下記 §3 GD-18）。
出典: https://learn.microsoft.com/en-us/entra/identity-platform/signing-key-rollover

## 2. 構成方針 — なぜこの骨格にしたか

### 2.1 参照した 2 系統

| 系統 | 例 | 特徴 |
|---|---|---|
| **商用 CIAM 型** | Auth0 / Okta（ライフサイクル軸）、Entra（**アプリ種別軸**）、Cognito | Quickstart・SDK・サンプルが厚い |
| **共有プラットフォーム運営者型** | **GOV.UK One Login / Login.gov / Singpass** | **統合前の意思決定 / 申請プロセス / サンドボックス / 本番移行 / サポート / Changelog** を独立章に持つ |

**本基盤は「セルフサービス SaaS」ではなく「グループ内共有基盤」**なので、**GOV.UK 型の骨格（オンボーディング → 決定事項 → 実装 → テスト → 本番 → エラー → サポート）× Entra 型のアプリ種別分岐**のハイブリッドを採用する。

### 2.2 商用 CIAM の目次だけ真似ると抜ける 6 項目（本ガイドでは独立章化）

統合前の意思決定リスト / クライアント登録の申請プロセス / サンドボックス / **本番移行手続きとローンチ後の変更手順** / サポート窓口 / ドキュメント変更履歴

### 2.3 Keycloak 公式ガイドだけ参照すると抜ける 5 項目

マルチテナント / レート制限 / リフレッシュトークンの扱い / セッション・ログアウト（KC は Server Admin 側にある） / 本番前チェックリスト

## 5. 未確認（原文直読が必要）

1. **RFC 10017 §8（トークン保存）の逐語 normative キーワード** — localStorage への `SHOULD NOT` の有無は原文確認が必要（GD-15 執筆時）
2. **OIDC Core §3.1.3.7 の項番割当**（原文 13 項目 / 取得結果 14 項目）— 内容は信頼可、項番参照時のみ要確認
3. 「アクセストークン有効期間が IdP 障害時のバッファになる」— 実務上の共通認識だが canonical な出典なし（GD-38 では推論として明示）
