# 利用者管理もアプリへ任せる場合の試算

> 🔴 **2026-09-02 訂正**: 本ノートの **§3「案 B」は前提の読み違い**でした。ユーザーの意図は「**顧客の認証システムに認証そのものを委ねる（自社で利用者を持たない）**」ではなく、「**IdP 本体は自社で構築するが、利用者の追加・削除と権限をアプリへ寄せる**」でした。**正しい試算は §7「案 C」**です。§3 は誤った前提の記録として残します。

- **日付**: 2026-09-02
- **種別**: research note（[minimal-scope-2026-09-01](minimal-scope-2026-09-01.md) の追加検討）
- **発端**: ユーザー問い「**利用者を追加・削除・編集する機能もアプリに任せるとすればどうか**」
- **結論（訂正後）**: 正しい前提は **案 C**（§7）= **2,395 → 2,122 人日（-273 / -11%）**。§2 案 A・§3 案 B は検討過程の記録。

## 1. 「アプリに任せる」の 2 つの解釈

| | **案 A: 画面だけ任せる** | **案 B: 利用者そのものを持たない** |
|---|---|---|
| 利用者の情報 | **本基盤が保持**（従来どおり） | **本基盤は保持しない** |
| 追加・削除・編集 | **本基盤が API を提供**し、アプリが呼ぶ | **顧客の認証システム側で行う**（本基盤は関与しない） |
| 管理画面 | **作らない**（アプリが自前で作る） | 作らない |
| 顧客の認証システムを**持たない**顧客 | **受け入れられる** | **受け入れられない** 🔴 |
| 本基盤の性格 | 認証基盤（自社でも認証できる） | **委譲専門の中継役** |

> 🔴 **案 B は「顧客の認証システムを持たない顧客は対象外」という事業判断**を伴う。技術ではなく**どの顧客を取るか**の話になる。

## 2. 案 A: 画面だけアプリに任せる

### 2-1. 何が減り、何が減らないか

| | 扱い | 理由 |

| **テナント越境の防止** | ✅ **残る（むしろ重要度が上がる）** | 🔴 **画面が無くなる分、API 側で止めるしかない** |

### 2-3. ⚠ 案 A の注意点

1. 🔴 **画面が無くなると、事故が API 側でしか止められない**
   これまで「画面で他テナントを選べない」ことが実質的な防御になっていた部分を、**すべて API の権限確認に寄せる**必要がある。**設計・試験の要求水準は上がる**。
2. 🔴 **顧客ごとにアプリが管理画面を作る**
   顧客が 10 社なら、**同じような管理画面が 10 個**作られる。§5-2（[前ノート](minimal-scope-2026-09-01.md)）と同じ構図。
3. 🟡 **本基盤の運用者向け画面は別途必要**
   顧客・接続先の登録は**我々の作業**でアプリに任せられない。ただし**件数が少なく、我々しか使わない**ため、**製品標準の管理コンソールで足りる**（自作しない）。
   → 自作管理画面（[ADR-038](../../adr/038-tenant-admin-portal.md)）の**そもそもの動機は「顧客に安全に開放するため」**なので、**顧客に出さないなら自作の理由が消える**。これは案 A の妥当性を支える。

## 5. 判断のポイント

### 5-1. 案 A の効果は限定的（-70 / 4%）

**「利用者管理をアプリに任せる」と聞いて期待する削減は、案 A では得られない**。理由は:

- **API は残さざるを得ない**（認証製品を触れるのは本基盤だけ）
- **画面が無くなる分、API 側の権限確認の設計・試験が厚くなる**
- **アプリ向けガイドが増える**

**効果が出るのは構築フェーズ（-45）**であり、**基本設計はほぼ変わらない（-3）**。

### 5-2. 案 B は効果が大きいが、事業判断

**-471（27%）と大きい**が、**「顧客の認証システムを持たない顧客を取らない」という判断**が前提。

**確認すべき 2 点**:
1. 🔴 **見込み顧客のうち、自社の認証システムを持たない割合はどれくらいか**
   （[ヒアリング B-BROK-1](../../requirements/hearing-checklist.md) の「委譲する比率」と同じ論点。**現在 50:50 の暫定値**であり、**もしこれが実勢なら案 B は半数の顧客を切ることになる**）
2. 🔴 **運用者自身の認証をどう確保するか**
   外部の認証システムに依存すると、**それが落ちたとき誰も入れない**。緊急時の入り口の設計が必要。

### 5-3. 中間案 — **案 B を段階導入する**

**最初は委譲専用で始め、利用者を収容する側は後から足す**という順序も採れる。

| | 内容 |
|---|---|
| **第 1 段階** | 委譲専用（案 B、1 クラスタ）で**認証システムを持つ顧客から開始** |
| **第 2 段階** | 需要が確認できてから**利用者を収容する側を追加** |
| 利点 | **初期投資を 1,272 に抑えつつ、選択肢を残せる** |
| 注意 | 🔴 **後から足すと 1,743 より高くつく**（2 度手間・移行作業）。**総額では不利** |

> **判断材料**: 「認証システムを持たない顧客がどれくらいいるか」が**確度高く分かっているなら段階導入は不要**（最初から決め打ちが安い）。**分からないなら段階導入で様子を見る**価値がある。

## 7. 【確定】案 C — IdP は自社構築、利用者管理と権限をアプリへ寄せる

### 7-1. 分担の確認

| 領域 | 担当 |
|---|---|
| **認証製品本体の構築・運用** | **本基盤** |
| ローカル利用者・パスワード・追加認証 | **本基盤**（IdP として成立させるため） |
| フェデレーション・接続先管理・停止の伝播・監査・インフラ | **本基盤** |
| **利用者の追加・削除・編集の操作** | **アプリ** |
| **権限とその連携** | **アプリ** |
| その他 | 本基盤。ただし**可能な限りアプリへ寄せる** |

### 7-2. 🔴 寄せきれない制約 — API は本基盤に残る

**認証製品の管理 API をアプリに直接叩かせることはできない。** テナント越境を止められず、**1 つのアプリの資格情報が漏れると全顧客の利用者を操作できてしまう**ため。

したがって利用者管理は「**画面だけ消えて API は残る**」という非対称になる。

| 機能 | 消えるもの | 残るもの |
|---|---|---|
| 利用者の追加・削除・編集 | **管理画面**（アプリが作る） | **API・テナント越境の防止・操作記録** |
| 権限の設定・判定 | **すべて**（権限用 DB ごと） | なし |

### 7-3. 91 機能の分類

| 区分 | 機能数 | WBS 行 | 内容 |
|---|---:|---:|---|
| **基盤** | **65** | 323 | 本基盤が作る |

| **アプリ移管** | **13** | 25 | 🔴 **本基盤から完全に消える** |
| **画面のみ移管** | **11** | 14 | 画面は消えるが **API は残る** |
| **追加移管候補** | **2** | 9 | **要判断**（下記 7-5） |

**完全に消える 13 機能**: 使えるアプリの設定 / アプリ内の役割の設定 / 権限の棚卸し・その定期起動 / 権限情報の一括取得 / 使えるアプリ一覧の取得 / アプリ利用可否の判定 / アプリ内の役割の解決 / 権限管理側の受け皿作成 / 参照用データの更新 / 初回ログイン者の識別子通知 / 識別子のアカウント間伝達 / アプリへの変更通知
