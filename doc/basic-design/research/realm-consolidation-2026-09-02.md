# 認証製品の統合（2 つ → 1 つ）— Realm 統合の決定

- **日付**: 2026-09-02
- **種別**: research note（構成の見直し 2 件目）
- **発端**: ユーザー判断「**B（Realm も統合）で提案したい**」
- **結論**: **受付用と収容用を 1 つの Realm に統合**。**① -26 / 全工程 -121**。

---

## 1. 何を統合するのか

**Realm** ＝ 利用者・接続先・鍵・ログイン画面・設定が丸ごと独立した空間。**Realm が違えば利用者も別**。

| | 現行 | **統合後** |
|---|---|---|
| クラスタ | 2 つ | **1 つ** |
| Realm | 受付用・収容用の 2 つ | **1 つ**（ブランドごと） |
| 利用者の所在 | 🔴 **控え（受付側）と実体（収容側）の 2 箇所** | ✅ **1 箇所** |

> **ブランドごとに Realm を分ける方針（[ADR-063](../../adr/063-brand-unit-architecture.md)）とは衝突しない**。ブランド軸はそのままで、**受付／収容の軸だけを畳む**。

---

## 2. 🔴 効果の本体は「設定が減ること」ではなく「同期が消えること」

**Realm 同士をつなぐこと自体は認証製品の標準機能**であり、設定作業に過ぎない。**重かったのは別のところ**にある。

**Realm が別 ＝ 利用者が 2 箇所にいる** ため、「**片方で止めたらもう片方も止める**」仕組みが必要だった。これが **17 行**を生んでいた。

| 消えるもの | なぜ消えるか |
|---|---|
| 内部 2 段構えの認証連携 | 委ねる先が自分自身になる |
| **停止の確実な伝播 / 再開の確実な伝播** | 🔴 **1 箇所で完結するため、伝える相手がいなくなる** |
| 初回識別子の通知 / 識別子・停止イベントのアカウント間配送 | 運ぶ相手がいなくなる |
| **送信予定イベントの記録（表・仕様）** | 伝える処理が無くなるため、記録も不要 |
| **停止伝播の突合（短間隔・日次）** | 🔴 **ずれが生じないため、拾い直す対象が無い** |
| 利用者の控えのライフサイクル設計 | **控えという概念自体が無くなる** |
| 収容側の構成・処理順序・設定値・スキーマ整理（4 件） | 受付側に統合される |

---

## 3. 🔴 失うものと、その扱い

| 失うもの | 影響 | 扱い |
|---|---|---|
| **パスワードのハッシュの物理分離** | 顧客の接続設定と同じ DB に同居する | 🔺 **DB の暗号化・接続元の限定・鍵の分離**で部分的に補う |
| **処理の重さの分離** | 🔴 **1 CPU あたりの処理能力が 10〜30 倍違う**ものが同居。**パスワード計算の集中でフェデレーションのログインまで詰まる** | 🔴 **PoC で裏取りが必要**（下記 §5） |
| 障害の分離 | 片方の障害が全体に波及 | 受容 |
| **2 ネットワーク分離の主目的** | 「ハッシュを守る」理由が消える | 🔺 **管理面の分離という別の目的は残る** → 別途再判断 |

## 5. 🔴 追加が必要な確認（PoC）

**処理の重さが違うものを同居させて成立するか**を実機で確かめる必要がある。

| 追加項目 | 人日 | 内容 |
|---|---:|---|
| **A-19** 🆕 | **+3** | **パスワード計算の集中が、フェデレーションのログインに与える影響の実測**。同一 Realm で両方の負荷を同時にかけ、**応答が悪化しないか**を確認する。悪化する場合の緩和策（処理の優先度・上限）も含める |

> **この確認を飛ばすと、本番で「パスワードログインが増えた日にフェデレーションが遅くなる」事象を踏む**。
