## 1. 分解の方針

| # | ルール |
|---|---|
| 1 | **人日は親行の予算を保存**して按分する（総量 473 は動かさない）。再見積りはしない — 詳細設計の中身は設計に入らないと分からないため、ここでやるのは「粒度と軸」の整備 |
| 2 | **DD-B（機能の詳細設計）は 1 行 1 機能**に分解。機能の一覧・重み・担当・スコープ・当初想定は **① WBS(基本設計) の HB-F-\* 行から継承**（重み = ①の機能別人日）。82 機能 = ①の 91 機能 − バッチ系 9（DD-F が受ける） |
| 3 | その他の 3 人日超の行は**作業の自然な軸**（画面群・API 入口群・監視の工程・試験対象群）で分解。0.5 刻み |
| 4 | レビュー（DDJ-01〜04）・継続管理（DDJ-05/06）は**1 イベント／継続活動のため分解しない**（①にも同型の 4〜8 人日行がある） |
| 5 | ID は**親 ID + 枝番**（例 DDA-07a）。ダッシュボードの `DD*` フィルタはそのまま生きる |
| 6 | 概要・完了定義は親行を継承し、枝の観点を付ける（DD-B 枝は「{機能名} の内部設計（処理の流れ・クラス構成・例外処理）。振る舞いは ①（出典列の HB-F-\*）で確定済み」で統一） |
| 7 | **9/2 の 2 決定をスコープ列へ反映**: 災害対策 = DDK-07 全枝を対象外／Realm 統合 = 伝播・控え・収容側・2 段構え系の行と枝を対象外。人日は残しフィルタで外す（ユーザー方針） |

## 4. ③構築（DU/BX 115 行）への軸付与 — 機能グループ・担当・スコープ

③構築の行は機能グループ・機能名が全行空欄だったため、担当 2 列が「横断扱い→全行基盤チーム」の一括値になっていた（案③比較が③で成立しない状態）。本節で **DU ごとに機能グループを付与し、担当 2 列・スコープを①から導出し直す**。

**導出ルール**:
- 機能グループが付く DU → 担当は①の同グループの値を継承（§3 の DD-B 分解と同じ）
- 横断（インフラ・NW・監視・運用・DR）→ 案②③とも基盤チーム
- **製品の設定（Realm/Flow/Mapper/Policy 等の Config）→ 案③ = 共同**（①r4「製品の設定は 1 つで全アプリに効くため分けられない」に準拠）
- **SPI・App・SPA・画面テーマ（製品の上に作る部品）→ 案③ = アプリチーム**（①r2「最初のアプリが認証製品の上の仕組みを全部作る」に準拠）
- スコープ: [dr-scope-decision §4-3](dr-scope-decision-2026-09-02.md)（③ -30 概算）と [realm-consolidation §2](realm-consolidation-2026-09-02.md)（消えるもの一覧）から、**丸ごと消える DU のみ対象外**とし、縮小に留まる DU は対象のまま備考に縮小見込みを記す（行の部分外しはフィルタ方針と両立しないため）
