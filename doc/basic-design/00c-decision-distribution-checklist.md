# 決定を追加したときの配布先チェックリスト

作成: 2026-08-18 / 目的: **「決めたのに、参照されるべき場所へ配られていない」漏れを構造的に減らす**

## 0. なぜこれが必要か

2026-08-17〜18 の全量突合で、**同じ構造の漏れが 4 系統で繰り返し**見つかった。

| 見つかった漏れ | 構造 |
|---|---|
| DR 表がアプリ層の決定（ADR-062 Lambda / ADR-064 EventBridge）に追随していなかった | **新しい決定 → 既存の表へ未配布** |
| `DU-U6-11`（内部 NLB TLS PKI）の DU はあるが U6 本文に設計が無かった | **WBS → 設計本文へ未配布** |
| `P-19` / `P-20` を採番したが全 8 単元へ未反映 | **前提 → 影響単元へ未配布** |
| 禁則 K-* が U9 に集約されたが主管単元へ戻っていない | **横断規約 → 主管単元へ未配布** |
| 監視対象に 5 サービスが入っていなかった | **サービス採用 → 監視項目へ未配布** |

**個別に直しても再発する。**決定を追加する行為に、配布先の確認を組み込む。

## 1. チェックリスト（決定 1 件につき通す）

### 1.1 必ず確認する 7 点

| # | 配布先 | 確認すること | 該当しなければ |
|---|---|---|---|
| 1 | **前提表**（[01 §1.1](01-architecture-baseline.md)） | 設計全体を縛る前提なら `P-xx` を採番したか。**ADR だけ作って前提表に載せない**と、影響範囲を機械的に追えなくなる | 前提でなければ不要 |
| 2 | **影響単元** | 前提表の「変更時の影響単元」に挙げた単元が、**実際にその ID を本文で参照**しているか | — |
| 3 | **DR 対象**（[08 §8.2.2 / §8.2.3](08-availability-dr-design.md)） | 新しいサービス・データを使うなら、**切替時にどうなるか**を書いたか。**事前設定が必要なもの（Secrets レプリカ等）は被災後に作れない** | ステートレスなら「IaC 再適用」と明記 |
| 4 | **監視**（[09 §9.1.2](09-operations-observability-design.md)） | **8 観点**（飽和/枯渇/期限/停止/滞留/逸脱/品質/沈黙、D-U9-22）のどれに当たるか。**該当する観点にメトリクスがあるか** | 監視不要なら理由を書く |
| 5 | **禁則**（[09 §9.5](09-operations-observability-design.md)） | 「やってはいけない」を含むなら `K-xx` に採番し、**主管単元の本文からも参照**したか | — |
| 6 | **コスト**（[コスト見積り](research/cost-unitprice-2026-08-17.tsv)） | 課金されるものを増やしたか。**費用が発生するなら必ず表に載る**ので、逆に「表に無い＝使っていない」の検査に使える | 費用ゼロなら不要 |
| 7 | **Runbook**（[09 §9.4](09-operations-observability-design.md)） | 運用手順を伴うなら `RB-xxx-nn` を紐づけたか。**必須 13 冊に入れるか**を判断したか | 手順不要なら不要 |

### 1.2 追記の位置（Excel と Markdown で分ける）

**Excel（進捗一覧・要件表シート）= 常に下へ追加する。**
- 行の挿入や ID の振り直しは、**Q 番号・条件付き書式・ソート・他シートの参照を壊す**
- 枝番化が必要なときも、既存行の下に枝番行を足す形にする
- 例: `NFR-OPS-001` を細分するなら、`NFR-OPS-001a`〜 を**表の末尾に足す**（元の行の直下に挿入しない）

**Markdown（設計書・要件定義）= 読んで分かる位置に置く。**
- 論理的に属する節へ入れる。末尾に積み上げない
- 節番号が埋まっている場合は `9.1.2a` `6.6.1a` のような枝番を使い、**該当箇所の直後**に置く
- 決定 ID（`D-Ux-nn`）は連番のまま末尾採番でよいが、**本文の配置は論理順**を優先する
- 既存の記述を置き換える場合は削除でなく**取り消し線 + 経緯**を残す（後から「なぜ変えたか」を追える）

**理由**: Excel は機械が参照する構造物で、位置の変更が副作用を生む。Markdown は人が読む文書で、論理順でないと理解が壊れる。**同じ「追記」でも最適な置き方が逆になる**。

### 1.3 あわせて更新するもの

- **WBS**（[00b](00b-design-unit-breakdown.md)）: 作業が増えるなら `DU-Ux-nn` を採番し人日を付ける
- **ヒアリング**（[hearing-checklist](../requirements/hearing-checklist.md)）: 顧客・アプリ・他組織の回答が要るなら起票し、**質問状にも設問を作る**
- **要件表**（[functional](../requirements/functional-requirements.md) / [non-functional](../requirements/non-functional-requirements.md)）: 要件の値が変わるなら是正する

## 2. 機械照合

手作業のチェックは漏れる。**[tools/check_design_consistency.py](../../tools/check_design_consistency.py)** が上記のうち機械化できる 5 つを検査する。

```
python3 tools/check_design_consistency.py           # 検出結果を表示
python3 tools/check_design_consistency.py --strict  # 検出があれば exit 1（CI 用）
```

| 検査 | 内容 | 根拠 |
|---|---|---|
| **A サービス網羅** | コスト見積り（= 使用サービスの全量）に対し、主管単元・DR で言及ゼロのものを検出 | **費用は必ず発生するので、コスト表は漏れのないサービス一覧になる** |
| **B 禁則の逆参照** | `K-*` が主管単元の本文から参照されているか | 禁則は U9 に集約されており、主管単元だけ読むと気づけない |
| **C 前提の追跡** | `P-*` の「影響単元」が実際にその ID を参照しているか | 前提が変わったときの影響範囲を追えるようにする |
| **D 監視の網羅** | 8 観点それぞれにメトリクスがあるか | 個別に足すだけでは同じ型の漏れが再発する |
| **E Runbook 整合** | 「必須 N 冊」の記載と列挙数が一致するか | 00a と U9 で 13 冊 / 14 冊の食い違いが実際にあった |
| **F ADR の配布** | ADR が設計書から参照されているか / ADR 索引に登録されているか | **ADR で決めたのに設計へ配られていないと、別名で二重起票される**。実例: ADR-047 の「暗号インベントリ」と D-U7-25 の「鍵インベントリ」が同一作業だった |

**検査 F の除外**: PoC 期・製品比較の ADR（001〜016 / 032 / 058）は設計から参照されないのが正常なため除外。`Superseded` / `Scope Reduced` / `凍結` / `廃止` / `Out of Scope` を含むものも意図的な無効化として除外する。**スコープ違い**（例: ADR-061 は API プラットフォーム側）は現状 UNITS のみを見るため誤検知しうる。

**限界**: 文字列照合なので、**単元が前提 ID を書かず値を直接書いている場合（「10M MAU」等）は検出できない**。C の検出は「トレーサビリティが切れている」ことを示すもので、設計上の欠落とは限らない。

## 3. 監視観点の 8 分類（[D-U9-22](09-operations-observability-design.md)）

チェックリスト #4 で使う。詳細は U9 を参照。

| 観点 | 何を捉えるか |
|---|---|
| 飽和 | 資源を使い切る（CPU / ディスク / 接続プール） |
| **枯渇** | **サービス側の上限に当たる（AWS クォータ）— 1000 IdP 規模で最初に当たる壁** |
| 期限 | 時間切れで止まる（証明書 / 鍵 / シークレット） |
| 停止 | 動くはずのものが動かない（バッチ / バックアップ） |
| 滞留 | 溜まって流れない（DLQ / outbox / レプリケーション遅延） |
| 逸脱 | 宣言と実態がずれる（IaC ドリフト） |
| 品質 | 遅い・失敗する（エラー率 / p99 / Burn Rate） |
| **沈黙** | **来るはずのものが来ない — 閾値監視では原理的に捉えられない。存在確認で設計する** |

| E Runbook 整合 | **0** | 必須 13 冊の定義を 00a / U9 で一致させた |
| F ADR の配布 | **0** | 6 本を精査（3 本 Superseded 化 / 3 本を設計へ接続 / ADR-061 索引登録） |

### 禁則の逆参照について（判断の記録）

当初「主管単元の改訂機会に随時」と保留したが、**検査が毎回 6 件出続けるとオオカミ少年化して見なくなる**ため方針を変えて解消した。

**調査の結果、6 件とも設計上の欠落ではなくトレーサビリティのみの問題**だった。実体は主管単元に存在しており、`K-n` の ID が無いだけである。検出された理由は、**単元が平易な日本語で書いていた**ため（例: `K-8` の `hideOnLoginPage=true` を U2 は「**IdP 一覧を UI に出さない**」と表現）。

逆参照は**見出しに `（禁則 K-n）` を添える形**にした。これにより検査が通るだけでなく、**単元を読んだ人が「これは破ってはいけない制約だ」と気づける**という本来の目的も満たす。
