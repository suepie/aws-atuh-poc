## 1. 何をお願いするか（結論）

各アプリの **デプロイパイプラインの最後に、監視資材 2〜3 ファイルを AWS S3 へアップロードする処理**を 1 ステップ追加してください。

```
デプロイ実行 → デプロイ成功 → 【追加】監視資材を S3 へアップロード
```

- 追加していただくのは**上記 1 ステップのみ**です。監視システムへの登録作業・登録用のコード実装は不要です
- アップロードされた資材は、弊社の監視基盤が **1 時間ごとに自動で取得**し、変更を検知して API の認証実装を検査します
- **御社のソースコードリポジトリへ弊社がアクセスすることはありません**

### 1.1 なぜ必要か

弊社では、公開している API が**認証を正しく実装しているか（未認証のリクエストを拒否できているか）を中央から継続的に検査**しています。認証設定の抜けは重大なセキュリティインシデントに直結するため、実際にリクエストを送って挙動を確かめる方式を採っています。

その検査には「**どの URL の、どの endpoint を、どの認証方式で検査すればよいか**」の情報が必要です。この情報を、御社のリポジトリを参照するのではなく、**デプロイ時にアップロードいただく資材から取得**します。

## 2. アップロードするファイル

### 2.1 置き場所

```
s3://auth-monitoring-artifacts-{アプリのAWSアカウントID}/
  {appId}/
    monitoring.yaml      ← 必須
    openapi.yaml         ← 必須（※後述の例外あり）
    deploy-info.json     ← 任意
```

- **バケットは弊社が事前に作成済み**です（作成不要）。バケット名は `auth-monitoring-artifacts-` + アプリをデプロイする AWS アカウント ID
- `{appId}` は、Service Catalog で製品を払い出した際に指定いただいたアプリ識別子と同じものを使用してください
- バケットはバージョニング有効です。**同名で上書きアップロードしてください**（旧版は自動で保全されます）

### 2.2 monitoring.yaml（必須）— 監視の宣言

**このファイルが存在すること自体が「このアプリを監視対象とする」宣言**になります。

```yaml
# {appId}/monitoring.yaml
appId: expense-api               # S3 のプレフィックスと同じ値にしてください（必須）
environments:
  prod:
    baseUrl: https://expense.example.com   # 検査先 URL（CloudFront の URL）
    authPattern: api-gw-jwt                # 認証方式（下表から選択）
  stg:
    baseUrl: https://stg.expense.example.com
    authPattern: api-gw-jwt
testTokenSecret: canary-central-readonly   # 省略可（省略時は共通の設定を使用）
```

| 項目 | 説明 | 必須 |
|---|---|:---:|
| `appId` | アプリ識別子。**S3 プレフィックスと一致必須**（不一致の場合は取り込まれません）| ✅ |
| `environments` | 環境ごとの検査設定。監視対象としたい環境をすべて記載 | ✅ |
| `baseUrl` | 検査先の URL。**CloudFront の URL** を指定してください（API Gateway の直 URL ではありません。実際の利用者と同じ経路で検査するため）| ✅ |
| `authPattern` | 認証方式。値は §2.5 の一覧から選択 | ✅ |
| `testTokenSecret` | 正規検査（有効なトークンでの疎通確認）に使うトークンの識別子。特段の事情がなければ省略してください | — |

> **記載しないでいただきたい項目**: アラートの通知先や監視の有効・無効フラグは、弊社側で一元管理します。資材には含めないでください。

### 2.3 openapi.yaml（必須）— API 仕様

検査対象の endpoint 一覧の情報源です。**デプロイした版**の OpenAPI 仕様を配置してください（御社リポジトリの正本をコピーしたもので構いません）。

**重要: 認証不要で公開する endpoint には、必ず公開印を付けてください。**

```yaml
paths:
  /_/health:
    get:
      x-synthetics-skip-auth-check: true   # ← 認証不要な endpoint に必ず付ける
```

- 監視基盤は「**記述のない endpoint はすべて認証必須**」と判定します（安全側に倒す設計です）
- したがって**公開印の付け忘れは、正しく公開している endpoint でも「認証漏れ」として最重要度のアラート**になります
- 逆に、認証が必要な endpoint には何も書く必要はありません

> **API Gateway を使わない構成（ALB 直のモノリス等）で OpenAPI 仕様が存在しない場合**は、`openapi.yaml` の代わりに monitoring.yaml へ endpoint リストを列挙する方式が可能です。該当する場合は弊社までご連絡ください。

### 2.4 deploy-info.json（任意）— 追跡情報

障害調査時に「どのバージョンがデプロイされていたか」を辿るための参考情報です。**監視の動作には影響しません**（付けなくても検査は正常に行われます）。

```json
{
  "commitId": "a1b2c3d4e5f6",
  "deployedAt": "2026-08-21T03:00:00Z",
  "pipelineRunId": "run-12345"
}
```

### 2.5 authPattern の選択肢

| 値 | 対象 |
|---|---|
| `api-gw-jwt` | API Gateway + JWT Authorizer（既定値）|
| `api-gw-lambda` | API Gateway + Lambda Authorizer |
| `api-gw-iam` | API Gateway + IAM 認証（SigV4）|
| `api-gw-cognito` | API Gateway + Cognito Authorizer |
| `alb-oidc` | ALB の OIDC 認証 |
| `app-cookie` | アプリ実装の Cookie セッション認証 |

※ 判断に迷う場合は弊社までご相談ください。誤った値を指定すると検査精度が落ち、警告が発報されます。

## 3. アップロードの手順

### 3.1 権限

**アプリごとに専用の IAM ロール `ArtifactUploadRole-{appId}` を弊社が払い出します**（アプリのデプロイ先 AWS アカウント内）。

- 権限は `{appId}/` 配下への **アップロード（PutObject）のみ**です（読み取り・削除の権限はありません）
- **デプロイに使用するロールとは分離**しています。デプロイロールに権限を追加する必要はありません
- 1 社で複数アプリを担当いただく場合も**ロールはアプリごと**です（他アプリの領域へは書き込めません）

### 3.2 CI から AWS への接続方法

**接続方式は、現在ご利用中の方式をそのままお使いいただけます**（アプリごとに異なっていて構いません）。代表的な方式は以下のとおりです。ご利用の方式をお知らせいただければ、それに合わせて上記ロールの信頼設定を行います。

| 方式 | 弊社へお知らせいただく情報 |
|---|---|
| OIDC フェデレーション（GitHub Actions 等）| OIDC プロバイダの発行者・リポジトリ / ブランチ等の条件 |
| 既存の IAM ロールからの引き受け | 引き受け元ロールの ARN |
| IAM ユーザーのアクセスキー | 対象 IAM ユーザーの ARN |

### 3.3 パイプラインへの追加例

デプロイが成功した後のステップとして追加してください。以下は AWS CLI を使う例です（お使いの CI ツールに読み替えてください）。

```bash
# ① 監視資材アップロード用ロールを引き受ける
ROLE_ARN="arn:aws:iam::${ACCOUNT_ID}:role/ArtifactUploadRole-${APP_ID}"
CREDS=$(aws sts assume-role --role-arn "$ROLE_ARN" --role-session-name artifact-upload)
export AWS_ACCESS_KEY_ID=$(echo "$CREDS" | jq -r .Credentials.AccessKeyId)
export AWS_SECRET_ACCESS_KEY=$(echo "$CREDS" | jq -r .Credentials.SecretAccessKey)
export AWS_SESSION_TOKEN=$(echo "$CREDS" | jq -r .Credentials.SessionToken)

# ② 監視資材をアップロード
BUCKET="auth-monitoring-artifacts-${ACCOUNT_ID}"
aws s3 cp monitoring.yaml "s3://${BUCKET}/${APP_ID}/monitoring.yaml"
aws s3 cp openapi.yaml    "s3://${BUCKET}/${APP_ID}/openapi.yaml"

# ③ 任意: デプロイ情報
cat > deploy-info.json <<EOF
{"commitId":"${CI_COMMIT_SHA}","deployedAt":"$(date -u +%Y-%m-%dT%H:%M:%SZ)","pipelineRunId":"${CI_RUN_ID}"}
EOF
aws s3 cp deploy-info.json "s3://${BUCKET}/${APP_ID}/deploy-info.json"
```

### 3.4 実行タイミング（重要）

**必ず「デプロイが成功した後」に実行してください。**

資材は「現在デプロイされている版の内容」であることを前提に検査が行われます。デプロイ前にアップロードすると、実際には反映されていない内容で検査され、誤った判定につながります。

デプロイが失敗した場合は、アップロードも実行しないでください（前回の資材が残り、実態と一致した状態が保たれます）。

## 4. アップロード後の流れ

| # | 起きること | 所要時間 |
|---|---|---|
| 1 | デプロイ成功 → 監視資材をアップロード | — |
| 2 | 弊社の監視基盤が巡回で資材の更新を検知し、内容を取り込む | **最大 1 時間** |
| 3 | そのアプリの全 endpoint に対して検査（未認証での確認 + 正常系の確認）を実施 | 上記の直後 |
| 4 | 問題があれば重大度別に関係チームへ通知 | — |

- **初回のアップロード時に自動的に監視対象として登録**されます（申請不要）
- 2 回目以降は、資材が更新されるたびに自動で再検査されます
- 資材に変更がない場合も、**1 日 1 回は全 endpoint の定期検査**が実施されます

---

## 5. 検査リクエストについて（ご承知おきください）

- 弊社の監視基盤から、**上記 `baseUrl` に対して定期的に検査リクエスト**が送信されます
- 検査には**認証情報を付けないリクエスト**が含まれます。したがって**アプリのアクセスログには定期的に 401 / 403 が記録されます**が、これは正常な動作です
- 検査リクエストには識別用のヘッダ（`X-Auth-Probe`）が付与されます。ログ上で区別が必要な場合はこのヘッダをご利用ください
- 検査は**参照系のリクエストのみ**で、データを更新する操作は行いません

## 6. 通知を受け取ったときの対応

| 通知 | 内容 | ベンダー側の対応 |
|---|---|---|
| **設定不備の通知** | monitoring.yaml の記載不備・欠落など | 資材を修正して再アップロード（次回巡回で自動的に再検査されます）|
| **認証漏れの疑い** | 認証が必要な endpoint が未認証で応答した | **最優先で確認・是正**をお願いします。弊社セキュリティ担当より別途ご連絡します |
| **資材が古い旨の通知** | 長期間アップロードがない | デプロイ運用と資材アップロードの整合をご確認ください |

## 7. 責任分担について

本仕組みの前提として、以下の分担でお願いしています。**契約・覚書への反映についてはお客様と別途協議のうえ確定します。**

| 項目 | 担当 |
|---|---|
| 資材バケット・アップロード用ロールの用意 | **弊社（共通基盤チーム）** |
| デプロイパイプラインへのアップロード処理の組み込み | **開発ベンダー各社** |
| **資材が正しくアップロードされていること・内容が実態と一致していること** | **開発ベンダー各社**（アップロード漏れ・記載誤りにより検査が正しく行われない場合の責は、原則としてアプリ側にあるものとします）|
| 監視基盤の運用・検査の実施・アラートの振り分け | **弊社（共通基盤チーム）** |
| 認証漏れが検知された場合の是正 | **開発ベンダー各社**（弊社は検知・連絡まで）|

> 弊社側でも、資材が長期間更新されていない場合の検知や、契約情報との突合による棚卸しを実施し、アップロード漏れの早期発見に努めます。ただし**これは補助的な検知であり、資材の正確性を保証するものではありません**。

## 付録: よくあるご質問

**Q. リポジトリへのアクセス権を求められますか。**
いいえ。弊社が参照するのは S3 にアップロードされた資材のみで、ソースコードにはアクセスしません。

**Q. アップロードを忘れるとどうなりますか。**
古い資材の内容で検査が継続されます。新しく追加した endpoint は検査対象に入らないため、認証漏れがあっても検知できません。§7 のとおり、この状態の責はアプリ側にあるものとしています。

**Q. 一時的に監視を止めたいのですが。**
資材の削除や改変ではなく、弊社までご連絡ください。監視の有効・無効は弊社側で管理しています。

**Q. 検査リクエストが WAF にブロックされませんか。**
検査リクエストを許可する設定を弊社にて行っています。ブロックされている疑いがある場合はご連絡ください。

**Q. ステージング環境も監視されますか。**
monitoring.yaml の `environments` に記載いただいた環境が対象です。記載しなければ対象外です。

**Q. 資材のフォーマットが正しいか、事前に確認できますか。**
検証用のスキーマファイルを配布予定です（別途ご案内）。
