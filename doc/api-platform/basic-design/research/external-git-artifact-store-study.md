# 外部 git（開発ベンダー保有）対応の資材置き場検討 v1

作成: 2026-08-21。**確定・設計反映済み（同日）**。案 A + deploymentId 併読廃止（資材オンリー原則）+ 責任分界（アプリ責・顧客合意）で確定し、設計書（04/10/12/13/16/17/18 章）・ADR-061・WBS v6・費用見積へ一括反映済み。本書は検討経緯の記録。

> **2026-08-21 ユーザー確定**:
> - **ART-Q-1 = 案 A で確定**（App アカウント S3 + 中央 pull 巡回維持）
> - **H-1**: アップロード用ロールは**デプロイロールと分離**する（App アカウントに専用アップロードロールを新設。s3:PutObject のみ・対象は自アプリ prefix 限定。StackSets で資材バケットと同梱配布）
> - **H-2**: ベンダーごとに複数アプリあり得る → **書込分離はアプリ（appId prefix）単位**（ベンダー単位にしない）
> - **H-3**: ベンダー CI → AWS の接続方式は**アプリごとに各々の方式で可**（アップロードロールを Assume できることだけをインターフェース要件とする）
> - **H-4（deploymentId 併読）**: メリデメ比較の上で判断待ち（ART-Q-7）。比較の要点 — 維持: 手動変更 1h 検知 + **資材アップロード忘れの機械検知**（S3 化で価値上昇）/ 廃止: 権限が s3 のみで説明容易だが上げ忘れ検知を失う。推奨 = **維持 + Resource を `/restapis/*/stages/*` に限定**（「デプロイ番号の確認のみ・構成監査ではない」を告知資料に明記。構成監査は Config Rules の役割）

## 0. 背景と問題

現行設計（[ADR-061](../../adr/061-deploy-detection-pull-model.md) / 17 章）は「**各 App アカウントの CodeCommit を中央がクロスアカウント read で巡回する**」ことが土台にある。しかし**コードリポジトリが開発ベンダーごとに外部（GitHub / GitLab / ベンダー自社ホスト等）にある**場合、この土台が成立しない:

- 中央の発見 Lambda から外部 git へは AssumeRole が使えない（AWS IAM の外）。ベンダーごとに認証方式・API・ネットワーク到達性が異なり、トークン管理・IP 許可・監査が N 社分発生する
- そもそもベンダーのリポジトリを当方が読む契約・セキュリティ合意が要る（ソース全体の閲覧権は過剰要求になりやすい）

→ **「git そのものを読みに行く」のをやめ、監視に必要な資材だけを S3 に置いてもらう**方式に切り替える。置き場所の 2 案を比較する。

### 0.1 監視が git から得ていたもの（＝S3 で代替すべきもの）

| # | 現行の依存 | 用途 | S3 での代替 |
|---|---|---|---|
| G-1 | monitoring.yaml（GetFile）| 監視宣言・検査先・authPattern・apiGatewayId | **資材としてアップロード** |
| G-2 | openapi.yaml（GetFile）| endpoint 一覧・公開印 MON-1 | **資材としてアップロード** |
| G-3 | 先端コミット ID（GetBranch）→ `lastCheckedCommitId` 比較 | **変更検知シグナル（git 主）** | **資材オブジェクトの VersionId/ETag 比較**（＋任意で deploy-info.json 内の commitId を参考値として受領）|
| G-4 | 変更パス（GetDifferences）| モノレポのアプリ特定 | **不要になる**（資材はアプリ単位でアップロードされるため、モノレポ問題自体が消滅）|
| G-5 | リポジトリ列挙（ListRepositories）+ monitoring.yaml 有無 | 監視対象の自動発見 | 規定プレフィックスの **List**（資材が置かれた = 監視対象）|

**重要な性質の変化**: git 巡回は「コミット＝デプロイ前」だったが、S3 アップロードを**デプロイパイプラインの最終段**に組み込めば「**資材あり＝デプロイ済み**」になる。現行の穴②「コミット ≠ デプロイ（未デプロイの偽安心）」は**構造的に縮小**する。代わりに新しい穴「**デプロイしたのにアップロード忘れ**」が生まれる（→ §3 で対策）。

### 0.2 前提の確認事項（ヒアリング要）

| ID | 確認事項 | 効くところ |
|---|---|---|
| H-1 | **App アカウントへのデプロイは誰がどこから行うか**（ベンダー CI が App アカウントのデプロイロールを Assume？ 内製パイプライン？）| アップロードを「デプロイと同じ主体・同じロール」に載せられるか。載せられれば追加クレデンシャル不要 |
| H-2 | ベンダー数と 1 ベンダー複数アプリの有無 | 書き込み権限の分離粒度（アプリ単位 prefix）|
| H-3 | ベンダー CI から AWS への既存接続方式（IAM ロール / アクセスキー / OIDC federation）| アップロード手段の標準（後述の告知資料に記載する設定）|
| H-4 | deploymentId 併読（apigateway:GET）の App アカウント read は維持可能か | ⑤' の存続（git が外れるため検知の 2 本柱の 1 本になる）|

## 1. 案の比較

### 案 A: 各 App アカウントの S3 に置く（分散置き場 + 中央 pull 巡回を維持）★推奨

- 各 App アカウントに **監視資材バケットを StackSets で配布**（DiscoveryReadRole と同じ配布網に同梱）
- デプロイパイプラインが最終段で `monitoring.yaml` / `openapi.yaml`（+ 任意 `deploy-info.json`）を**自アカウントのバケットに Put**
- 中央の発見 Lambda は従来どおり **1 時間毎に AssumeRole → List/Get で巡回**し、**VersionId/ETag の変化**で M1（自動差分検査）を起動

### 案 B: 共通基盤アカウントの 1 バケットに集約（各ベンダーが中央へ push）

- 中央に集約バケット（例: `uploads/{appId}/…`）を置き、各アプリのデプロイパイプラインが**クロスアカウント Put**
- 発見 Lambda の巡回は自アカウント内の List だけになり、クロスアカウント read が deploymentId 併読（apigateway:GET）だけに縮小

### 比較表

| 観点 | 案 A: App アカウント S3（pull 維持）| 案 B: 中央集約 S3（push 復活）|
|---|---|---|
| **ADR-061 の原則**（読み取り専用・登録漏れゼロ構造）| ✅ **維持**。クロスアカウントは read のみのまま | ⚠ **「App→中央の書き込み」経路が復活**（ADR-061 が廃止した旧 push 型の再来。付録の 5 案比較で S3 案として検討済み）|
| 攻撃面・設定ミス面 | 読み取り 1 方向のまま最小 | 中央バケットへ N 主体の書込を開放。**prefix ごとの書込分離（bucket policy で `{appId}/` に制限）を全アプリ分正しく維持**する必要。誤設定＝他アプリ資材の上書き・なりすまし |
| 登録・アップロード漏れの検知 | 巡回が「バケットはあるのに資材が無い/古い」を毎時検知できる（バケット自体は StackSets で必ず存在）| 同等のことは可能だが、「そもそも書き込み権限設定がされていないアプリ」は中央から見えにくい |
| ベンダー側の作業 | デプロイ先アカウント内への Put（**デプロイロールに s3:PutObject を足すだけ**。追加クレデンシャル不要の可能性大 = H-1）| 別アカウント（中央）への Put。クロスアカウント権限 or 専用ロールの払い出し・管理が N 社分 |
| 中央の実装 | 現行巡回の読み先を CodeCommit→S3 に差し替え（構造同一）| 巡回は簡素化するが、書込側の権限管理・検証（改ざん・上書き対策）が新設 |
| バケット数・IaC | アカウント数分（StackSets で機械配布、暗号化・Versioning・ライフサイクル込みテンプレ）| 1 個（ただし policy が肥大）|
| 監査 | 各 App アカウントの CloudTrail に Put が残る（アプリ資産として自然）| 中央の CloudTrail に集中（見やすいが、書き手の否認防止はロール設計次第）|
| **総合** | **◎ 変更が局所的で原則も守れる** | △ 集約の見た目は良いが、セキュリティ設計の後退と権限運用の増加 |

> 参考案 C（外部 git を直接読む）: ベンダーごとの認証・到達性・契約・トークン運用が N 社分発生し、標準化できないため不採用。個別ベンダーが希望しても「S3 に置く」インターフェースに寄せる（git→S3 の橋渡しはベンダー CI の責務）。

**推奨: 案 A**。理由の核は「**ADR-061 で一度捨てた『中央への書き込み開放』を復活させない**」こと。案 A はアーキテクチャ原則（pull・read-only・中央が発見する側）を保ったまま、読み先だけを CodeCommit→S3 に差し替える最小手術で済む。

## 2. 案 A の設計スケッチ（確定後に 17 章へ正式反映）

### 2.1 資材セットと置き場所（規約案）

```
s3://auth-monitoring-artifacts-{accountId}/        ← StackSets 配布（App アカウント、Versioning 有効）
  {appId}/
    monitoring.yaml      # 現行 §17.3 と同一書式（apiGatewayId/stage 含む）
    openapi.yaml         # spec 正本のコピー（デプロイした版）
    deploy-info.json     # 任意: { commitId, deployedAt, pipelineRunId } — 追跡用参考値
```

- **「{appId}/monitoring.yaml が置かれている = 監視対象」**（現行の「リポジトリに monitoring.yaml がある = 監視対象」と同型）
- アップロードは**デプロイパイプラインの最終ステップ**（デプロイ成功後に Put）。IaC/パイプラインテンプレに組み込み、ベンダー告知資料に手順を明記（→ ユーザー要望の「アナウンス」対象）
- 変更検知: 発見 Lambda が **オブジェクトの VersionId を台帳の前回値と比較**（ETag はマルチパートで MD5 と一致しない場合があるため VersionId 主・ETag 副）

### 2.2 巡回フロー（17 §17.2.1 の差し替えイメージ）

| 現行ステップ | 変更後 |
|---|---|
| ① アカウント列挙（Organizations 委任）| **不変** |
| ② AssumeRole（DiscoveryReadRole）| **不変**（権限だけ変更、§2.3）|
| ③ ListRepositories | **List `s3://…/` の {appId}/ プレフィックス** |
| ④ GetBranch → lastCheckedCommitId 比較 | **monitoring.yaml / openapi.yaml の VersionId 比較**（台帳 `lastArtifactVersions`）|
| ⑤' deploymentId 併読 | **不変**（git が外れる分、挙動レベル検知の柱として重要度が上がる）|
| ⑥ GetDifferences + GetFile | **GetObject**（変化した資材のみ）。モノレポ特定処理は**削除** |
| ⑦ M1 起動 + 台帳更新 | ほぼ不変（更新値が commitId → VersionId に）|
| 新規発見 / 消滅検知 | 同型（prefix 出現 = 自動登録 / monitoring.yaml 消滅 = enabled=false + 棚卸し）|

### 2.3 IAM（16 章の差し替えイメージ）

DiscoveryReadRole の権限: `codecommit:*` 5 アクションを削除し、以下に置換:

```
s3:ListBucket（資材バケット限定・prefix 条件）
s3:GetObject / s3:GetObjectVersion（資材バケット/*）
apigateway:GET（現行どおり）
```

漏洩時影響は「ソースコード閲覧」→「**監視資材（yaml/spec）と API GW 構成の閲覧**」に縮小（ソース全体が見えなくなる分、現行より機微性は下がる）。

### 2.4 検知の穴の再評価（17 §17.2.2 の書き換えイメージ)

| 穴 | 現行（git 主）| 案 A 移行後 |
|---|---|---|
| コンソール直変更 | deploymentId 併読 + Config Rules + ガイド | **不変**（三重補完のまま。git 喪失の影響なし）|
| コミット ≠ デプロイ（未デプロイの偽安心）| 次回巡回 + 全量検査 | **構造的に縮小**（アップロード＝デプロイ後のため、資材と実態のズレが起きにくい）|
| **（新）デプロイしたのにアップロード忘れ / CI 未整備** | — | **deploymentId 併読が検知**（deploymentId が変わったのに資材 VersionId が変わらない → 「資材の更新漏れ」としてメタ不足系アラート）。ALB 直は資材の staleness（`deployedAt` が古い/欠落）+ 棚卸しで補完 |
| **（新）資材の改ざん・なりすまし** | —（git は PR レビューで統制）| バケットへの書込をデプロイロールに限定（bucket policy）+ Versioning で履歴保全 + `baseUrl` はドメイン許可制（probe の宛先 allowlist を CloudFront ドメインパターンで検証、現行の代償統制を強化）|

### 2.5 変わらないもの（影響なしの確認）

probe/classify/4×4（11 章）、Alert Router / SNS（15 章）、Monitoring Registry（中央 S3、12/13 章の**中央側**構造）、MON-1 公開印、Positive トークン管理、WAF 干渉対策、Config Rules（②）、全量検査（モード2）の日次+手動、メタ監視 MM-1〜5、Lambda 3 本・VPC 外、NW-2 例外。**Lambda の本数・配置は不変**。
