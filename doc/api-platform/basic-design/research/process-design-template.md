## 1. なぜ処理単位に分解するか

10-18 章は**領域ごと**（構成・実行モード・検知・台帳・IAM…）に書かれており、レビューと合意には適するが、**実装・単体テスト・運用手順の起点にはならない**。そこで「1 つのトリガから 1 つの結果までの最小単位」＝**処理**に割り、処理ごとに I/O・手順・例外・権限を確定する。この粒度が WBS の `-d`（設計）成果物と 1:1 対応する。

## 3. 処理分解カタログ（SSOT）

> 【注意】この表を変更したら `tools/process_catalog.py` の `PROCESSES` も同時に更新すること（Excel はそこから生成される）。

### 3.1 処理 ID の付け方（系統）

処理 ID の接頭辞は**実行主体（Lambda 名）に揃える**。あわせて `実行契機` 列で「いつ動くか」を示す。

| 接頭辞 | 実行主体 | 動くタイミング | 備考 |
|---|---|---|---|
| **対象検索** | 対象検索 Lambda | 1 時間毎の巡回 | 変更検知・登録までを担う |
| **全量** | 認証実装チェック Lambda | 日次定期 + 手動 | 同 Lambda の処理のうち**全量確認固有**（起動・全件取得・アプリ単位への割り振り）|
| **認証実装チェック** | 認証実装チェック Lambda | **対象検索起点・全量起点の両方**（共通）| 同 Lambda の処理のうち**1 アプリの確認** |
| **通知** | アラート検知 Lambda / CloudWatch | 検知時 | |
| **運用** | CloudWatch / 運用者 | 随時（異常時・運用操作）| |
| **連携** | ベンダー CI | デプロイのたび | アプリ側の責務 |

**この分け方にした理由**: 「巡回 / 全量 / 手動」だけで分類すると、**1 アプリの確認処理（8 件）と通知（3 件）が対象検索起点でも全量起点でも同一**であるため、大半が「共通」に落ちて接頭辞が情報を持たなくなる。そこで **① 実行主体の Lambda 名を接頭辞にし、② 同じ Lambda 内で実行契機が分かれる部分（全量確認固有）だけ 全量 として切り出した**。手動は「全量確認の起動元が人である」ケース（全量-02）と運用操作（運用-03）に限られるため、独立系統にせず `実行契機` 列で表す。

各処理シートと処理一覧には **`実行契機` 列**があり、「対象検索（1 時間毎）/ 全量（日次）/ 全量（手動・随時）/ 共通（対象検索・全量とも）/ 随時」で個別に判別できる。

## 5. 記載のルール

1. **設計の正は md（10-18 章）**。本 Excel は処理単位に展開した実装・テスト用の器であり、**md と矛盾したら md が勝つ**
2. 各処理シートの「基本情報」「権限・エンドポイント」は md から機械的に転記済み。**空欄になっているのは設計者が埋める箇所**
3. 未決は各シート §11 に書き、`03_処理一覧` の未決列にも反映する
4. 1 処理 = 1 トリガ = 1 結果。分岐が 2 系統以上ある場合は処理を分割する
5. **単体テスト観点は §2/§3/§6 から起こす**（I/O の境界値と例外ケースがそのままテストケースになる）
6. 【注意】**記入は Excel に直接せず、`tools/process_catalog.py` に書く**（次節）。Excel のシート 18 以降は生成物で、再生成すると手入力は消える

## 6. 記入の仕方（詳細を SSOT 側に持たせる）

シート 18 以降は `tools/process_catalog.py` から生成されるため、**Excel に直接書いた内容は再生成で失われる**。そこで各処理の設計内容は `PROCESSES` の各 `P(...)` に **`d=dict(...)`（詳細）** として書く。`d` を与えた欄は**白セル（記入済み）**で、与えていない欄は**黄色（記入待ち）**で生成される。

```python
P("認証実装チェック-04", "未認証アクセス確認", …,
  d=dict(
    position="フロー内の位置",
    pre=["前提条件を箇条書き", "…"],
    inputs=[["項目", "型", "必須", "取得元", "説明・例"], …],
    outputs=[["項目", "型", "出力先", "説明・例"], …],
    steps=[["処理内容", "補足・参照"], …],          # 番号は自動付番
    exceptions=[["ケース", "検知方法", "動作", "通知", "参照"], …],
    idem=("再実行時の振る舞い", "状態更新のタイミング"),
    authnote=["認証方式・補足", …],
    logs=[["種別", "名称・項目", "内容", "備考"], …],
    perf=("想定件数 / 所要時間", "上限・制約"),
    opens=[["ID", "内容", "確認先", "期限"], …],
  ))
```

**書き方の指針**（認証実装チェック-04 を基準とする）:

| 節 | 押さえること |
|---|---|
| 入力 / 出力 | **取得元・出力先を必ず処理 ID で書く**（「認証実装チェック-02（extractEndpoints）」のように）。どの処理から来てどこへ渡るかが辿れないと単体テストが書けない |
| 処理手順 | 1 ステップ = 1 動作。**補足列に必ず「なぜそうするか」と md の節番号**を書く（例「11 §11.2.4」）。実装者が判断で崩さないため |
| 例外 | 「何が起きたら / どう気づいて / どう振る舞い / どこへ通知し / 根拠はどこか」の 5 点セット。**正常系の分岐（スキップ等）もここに書く** |
| 冪等性 | **状態を更新するか否かを最初に明言**する。更新しないなら「更新しない」と書く（次の処理との責務境界がはっきりする）|
| ログ | 出す項目を列挙し、**マスク対象を明記**（OBS-3）。メトリクスを出さない処理は「出さない・どこで出すか」を書く |
| 性能 | 想定件数の**根拠**（費用見積の P-* など）を添える。実測待ちなら「W3-5 で確定」と書く |
| 未決 | 既存の `M-Q-*` は ID を引用。**新たに見つけた論点は md（10-18 章）側に採番して登録**してから、ここに引く |

> 【注意】**新しい未決を見つけたら、必ず md の該当章の未決表へ登録する**。処理設計シートだけに書くと SSOT から漏れる。
> 例: 認証実装チェック-04 の設計中に「Negative probe が更新系メソッドを叩くと、認証漏れ時に本番データを更新してしまう」ことが判明 → **M-Q-11-6 として 11 §11.5.1 / §11.9 に登録**した。
